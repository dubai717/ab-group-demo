# تجربة AB Group محلياً على Windows 11

الرابط بعد نجاح التشغيل: **http://127.0.0.1:3100**. لا يوجد Backend منشور دائماً؛ سينشئ المشغّل عملية Backend محلية تتصل بقاعدة Supabase التجريبية الحالية، ويقدّم الواجهة نفسها من الأصل نفسه. لا يشغّل خادم العرض التجريبي القديم على المنفذ 3000.

## مرة واحدة

1. ثبّت **Node.js 24 LTS** من https://nodejs.org/en/download إذا لم يكن مثبتاً. لا يحتاج Git أو Docker أو اشتراك إضافي. أغلق نافذة التشغيل القديمة بعد تثبيت Node لتحديث PATH.
2. حمّل ZIP فرع `feature/central-database-foundation`، وفكّه في مجلد محلي موثوق غير عام/مشترك وغير متزامن مع خدمة مشاركة. افحص الملفات قبل تشغيل `Start-ABGroup.cmd` بالنقر المزدوج. لا تشغّل النسخة القديمة من main.
3. في النافذة المحلية فقط، أدخل القيم الأصلية الخمس عند الطلب (الإدخال مخفي): `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `DATABASE_URL`, `DATA_ENCRYPTION_KEY`. استخدم نفس مشروع الاختبار والمفتاح الحاليين، ولا تولّد بديلاً. GitHub لا يتيح قراءة قيم Secrets المحفوظة؛ يجب استخدام النسخ الأصلية المحمية لديك. لا ترسلها في المحادثة.
4. لإنشاء حساب الواجهة الوهمي الجديد فقط، أدخل `MIGRATION_DATABASE_URL` الحالي مرة واحدة؛ لا يُحفظ. اختر كلمة مرور دخول جديدة للحساب الوهمي وأكدها. يعرض المشغل اسم الدخول `trial_…`؛ احتفظ بكلمة مروره في مدير كلمات مرورك. لا تستخدم كلمة مرور قاعدة البيانات للدخول.

ينفذ المشغل تثبيت dependencies المثبتة في lockfile دون أسرار أو install scripts، ثم إنشاء مجموعة/مالك وهميين منفصلين، ثم تشغيل الواجهة تلقائياً بعد نجاح فحص جاهزية الاتصال. لا يغيّر أي مستخدم أو مجموعة أو صلاحية قديمة، ولا يطبّق ترحيلات أو يغيّر كلمة مرور ab_runtime. إعادة المحاولة تتعرف إلى المالك الوهمي نفسه وتتحقق من كلمة مروره دون إعادة تعيينها؛ إذا انقطعت التهيئة، استخدم كلمة مرور الدخول نفسها لإكمالها. لا يوجد حذف تلقائي عند الفشل.

القيم الخمس مشفّرة باستخدام **Windows DPAPI للمستخدم الحالي** في `%LOCALAPPDATA%\ABGroupERP\supabase-test\vault.dpapi.json`، خارج المستودع، مع ACL للمستخدم الحالي وSYSTEM فقط. هذه خزنة محلية مشفرة وليست backend.env أو ملف أسرار مكشوفاً. لا يحتاج المشغل وحدة PowerShell أو خدمة جديدة. كلمة مرور حساب الواجهة واتصال الإدارة لا تُحفظ فيها. هذه الحماية لا تعزل البرامج التي تعمل بحساب Windows نفسه أو مدير النظام؛ استخدم جهازاً وحساب Windows موثوقين. لا تنقل ملف DPAPI إلى جهاز/حساب آخر باعتباره نسخة احتياطية قابلة للاستخدام.

تُمرر الأسرار إلى عملية Node عبر بيئتها الخاصة فقط، وليس command line أو ملفات env أو متغيرات مستخدم دائمة. عملية الويب لا تستقبل MIGRATION_DATABASE_URL أو كلمة مرور التهيئة. لا تطبع القيم أو أخطاء المزود الخام. لا تستخدم Transcript أو أدوات تسجيل جلسة أثناء إدخالها.

## تجربة الواجهة

- سجّل الدخول بالاسم الظاهر وكلمة مرور حساب الاختبار التي اخترتها.
- افتح الشركات والكيانات، وأنشئ شركة وهمية واحفظها؛ افتحها من السجل وتحقق من البيانات.
- افتح الحسابات البنكية، واختر الشركة الوهمية، وأضف حساباً وهمياً واحفظه ثم أعد فتحه. استخدم أرقام اختبارية فقط.
- حدّث الصفحة، ثم أغلق المتصفح وأعد فتح الرابط للتحقق من الاسترجاع المركزي. يمكنك إضافة حساب ثان للشركة نفسها.
- تبقى نافذة المشغل مفتوحة طوال التجربة. اضغط Enter داخلها لإيقاف Backend المحلي فقط؛ لا تُحذف سجلات Supabase. في المرات التالية افتح Start-ABGroup.cmd؛ لا يُعاد طلب الأسرار بعد نجاح التهيئة، ويظهر اسم المستخدم نفسه.

لا تدخل بيانات حقيقية. المرفقات تبقى في الحجر حتى تجهيز فاحص فعلي. التشغيل محلي على loopback فقط؛ لا تغيير Firewall، ولا نفق عام، ولا نشر أو دمج #10/#11. صلاحيات حساب المالك الوهمي محصورة بمجموعته الوهمية ولا تعدّل المالك الحالي.

## تصحيح إدخال خاطئ

من PowerShell داخل مجلد النسخة شغّل:

```powershell
.\Start-ABGroup.cmd -Setup
```

أدخل القيم الأصلية الصحيحة من جديد، ولا تدوّر المفاتيح أو تغيّر مشروع الاختبار. لا تشارك الخزنة أو screenshots للمدخلات. إذا لم تعد لديك نسخة أصلية من أحد الأسرار، توقف وأبلغ باسم السر فقط؛ لا نحاول استخراج قيم GitHub Secrets إلى السجلات.

## تحقق التجهيز

نجح TypeScript وثلاثة اختبارات محلية جديدة: إنشاء المالك الوهمي وإعادة استخدامه دون تكرار/إعادة تعيين، منع التهيئة خارج السياق المسموح دون تسريب، وفصل عملية الإدارة/الويب. فحص Windows الأصلي في `.github/workflows/windows-local-launcher-check.yml` لا يملك أسراراً ولا يتصل بـSupabase؛ يفحص syntax وDPAPI وACL وبيئة العملية المعزولة. نجاح اختبارات Supabase السابقة لا يعني أن متصفح Windows لدى المستخدم شُغّل بالفعل.


**نتيجة Windows الفعلية:** نجح [تشغيل 41446260038](https://github.com/dubai717/ab-group-demo/actions/runs/41446260038) على Windows/Windows PowerShell بعد إصلاح اختيار مسار Node واحد: parsing وDPAPI وACL والحفظ المشفر وعزل بيئة child وloopback listener. لم يستقبل أسرار Supabase ولم يغيّر أي بيانات سحابية. بقي اختبار التفاعل من متصفح جهاز المستخدم بعد إدخال أسراره محلياً؛ لا ندعي أنه تم عن بُعد.
