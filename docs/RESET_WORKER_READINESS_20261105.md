## Implemented path

Owner settings → server session/CSRF/primary-Owner check → server-side preview job → encrypted retained backup and isolated restore proof → current Owner password reauthentication → expiring session/Owner/scope-bound confirmation + typed phrase → privileged GitHub Actions worker. The web/browser never receives the administrative database connection. Passwords are neither persisted nor logged. Status tokens live in page memory and reveal only job state.

The fixed target is the existing original staging service/project. Production, another project/ref/workflow, absent activation, wrong deployed release, stale/changed scope, unsupported identity recovery, non-private storage, unexpected buckets and missing/failed backup all stop execution. This is a full environment reset, not a TEST_DATA filter: every business/history table and every mapped non-primary-Owner identity is in the preview, including accounts created manually during testing.

Maintenance is encrypted in the private bucket outside the replaceable schema. All API requests and background Core transactions fail closed; shared/exclusive advisory locking drains writes. A worker crash leaves maintenance active. Ordinary deployment checks that marker and stops while reset/recovery is active. Reset and delivery share a non-cancelling concurrency group.

Only application schema `ab` is rebuilt transactionally from checksum-approved migrations 001–013. Catalogs, schema definitions, table grants, RLS, triggers, constraints, functions and outside-schema definitions must match before commit. No trigger/RLS disabling, forced row deletion or TRUNCATE is used. Managed `auth`/`storage` namespaces are never dropped; canonical Supabase APIs remove non-Owner identities and approved business object keys. Backup/control prefixes are protected.

The original primary Owner's complete profile, auth_id and Auth row/password verifier are preserved. Approved catalogs, primary organization, emirates/areas/aliases, neutral references and primary-system settings are restored; stale test registries and reset intents are not. The exact previously identified synthetic `demo-bank` and TEST-generated financial chart are not treated as neutral configuration. Unexpected catalog/schema differences block the reset, rather than discard new definitions.

After a failure following commit, hash-preserving supported Auth Admin imports, application-schema restore and digest-checked file restore run under maintenance. Old Auth refresh sessions are deliberately not reimported; users must sign in again. Failed/unverified recovery keeps the service fenced. Explicit recovery requires the matching request id approval; no blind retry or success claim.
