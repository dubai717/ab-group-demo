# Authentication transition — review required before enabling real password operations

## Current inspection and approved scope

The base is `main` at `8f25b79`. No `AGENTS.md` was found in the workspace. `server.js` is a static Node HTTP file server, not an authentication service; there is no user database, session service, verified-contact registry or notification provider. `app.js` compares demo usernames/passwords and persists its existing application state in localStorage. Existing demo passwords and client-asserted roles are not a production security boundary.

This change preserves that demo login and all existing stored users/roles. It does **not** migrate or overwrite credentials. The earlier local user-management development remains on its independent branch; this PR adds only password-flow presentation to current main.

The new module never stores submitted passwords, OTPs or recovery identifiers. It makes no authentication/provider requests. No OTP is generated, no message is claimed to have been sent, no local password verification is presented as secure, and no password operation can return success. Valid-looking password submissions are explicitly rejected as backend unavailable. Existing demo authentication/storage is still unsuitable for real credentials; do not use real accounts or personal data.

## Implemented interface

- Existing login design, official image, colours, Arabic/English and RTL/LTR are retained. Password visibility no longer clears typed credentials. Failed login (including inactive accounts) uses a generic message.
- Forgot-password link below the password field; username/email/phone input; SMS/email/WhatsApp channel selection. These are **planned channels**, not claims that a user's contact has been verified. Every request has the same unavailable outcome independent of account existence. Input is cleared after submission.
- Verification and new-password steps are visibly unavailable and disabled until actual backend verification. No locally generated code, reset credential, expiry timer or “successful reset” screen exists.
- Administrator-assisted recovery guidance: no request is actually sent. A future privileged recovery action needs explicit authorization and trusted identity checks; it must never disclose the old password or allow an operator to bypass the owner's protection.
- Personal menu → Account settings → Change password. The actor comes from `getCurrentUser()`, not an editable target-user field. Every signed-in role can open it without administrator approval. Current/new/confirmation inputs have client format checks; submitted fields are cleared. Even a valid format does not verify the current password or save a new one.
- The preliminary UI policy is 12–128 characters, uppercase/lowercase/digit/symbol, no whitespace, new value different from current, and matching confirmation. A server policy and breached-password blocklist must be finalized before activation.
- A bounded in-memory interface event log records event types, timestamp, canonical demo actor ID (authenticated events only) and allowlisted channel. It records no entered identifiers, passwords, OTPs or contact details. Account events are scoped to the actor and removed on logout; all events disappear on reload. This is not a durable or tamper-resistant server audit log.

## Proposed backend and activation sequence (not implemented or authorized for deployment)

1. **Build and test in isolation.** Add a private user database and credential store, authenticated sessions using Secure/HttpOnly/SameSite cookies, CSRF protection, TLS and a server-side permission boundary. Disable demo-login buttons in the future production build. Never accept browser-supplied role or target-user claims. Keep this demo runnable while backend integration is reviewed.
2. **Migrate without changing access silently.** Review backups and map existing user IDs, owner identity, role permissions and memberships. Import permitted profile data with a reviewed migration; real users must enrol or reset securely. Do not import plaintext demo credentials into production. Verify owner and general manager access in staging before switching login. Switching authentication, migrating data and disabling the old mechanism require a separate review/approval.
3. **Store credentials securely.** Use a salted password hash such as Argon2id with deployment-tuned cost. Keep secrets and provider credentials on the server. Do not write plaintext passwords, OTPs or reset tokens into localStorage, browser caches, logs or analytics. Password change verifies the current credential server-side and updates only the authenticated actor in an atomic transaction. Reject reuse; validate the full server policy and breached-password list. Invalidate/reset other sessions according to policy after a real change.
4. **Enroll verified contacts.** Store normalized email and E.164 phone values plus per-channel verification/consent timestamps. WhatsApp must be an explicitly verified and consented destination, not an inferred channel simply because a phone number exists. Prevent unverified recovery-contact changes from taking effect. Only verified channels may receive recovery messages.
5. **Connect providers.** SMS requires a gateway, approved sender, delivery receipts and server-held credentials. Email requires a transactional mail provider, verified sending domain (SPF/DKIM/DMARC) and reset templates. WhatsApp requires an approved Business API/provider, approved authentication template and recipient opt-in. Use background delivery jobs, idempotency and provider error monitoring. No API keys, complete contact data or provider status should leak into anonymous responses.
6. **Design non-enumerating recovery.** A proposed request endpoint accepts identifier + requested channel and returns the same generic response for existing/nonexistent/inactive/unverified accounts, with consistent timing and rate limiting. Never return full contact details or an account-specific channel list to an anonymous claimant. Use a staged, verified challenge before revealing any account-specific options. Deliver only to the canonical verified destination from the database, never to a destination supplied in the request. Do not return an OTP to the client or send the old password.
7. **Enforce lifecycle on the server.** Initial proposed limits for review: OTP validity 5 minutes, at most 5 verification attempts per challenge, resend cooldown 60 seconds, and layered per-account/per-destination/per-IP request budgets (e.g. 5 per hour), with abuse monitoring. Generate codes/tokens using a cryptographically secure generator; store OTP verifiers using a server-secret keyed hash and reset-link tokens as hashes, with expiry, purpose and account binding. A resend invalidates the old challenge. The final reset authorization is short-lived, single-use and consumed atomically; reject expired, exhausted, reused, mismatched or concurrently redeemed challenges. A browser timer is never authoritative.
8. **Reset and notify only after real verification.** On successful verification, issue a restricted reset authorization that cannot modify another account or access general APIs. Apply the new password server-side, invalidate challenges/sessions as appropriate, append an audit event and enqueue a change notification to verified contacts after commit. Only then may the UI display success. Notifications contain no password or reusable token.
9. **Privileged fallback.** Introduce a narrowly scoped recovery permission for authorized administrators, separate from ordinary profile edits. Require strong operator authentication, trusted identity proofing outside lost channels, protection against contact substitution, special owner-account safeguards, and a durable audit trail. Issue a single-use enrollment/reset invitation through a verified alternate process; never show a password to the operator. The exact fallback/owner policy needs approval before activation.
10. **Stage, review and cut over.** Integrate the UI with tested backend endpoints behind an explicit configuration/feature gate; fail closed when unavailable. Run security and regression tests, review the credential migration and rollback plan, then request approval before switching login or deploying. This PR does not add a hidden stub backend or a client OTP validator.

Suggested future contracts: `POST /auth/recovery/request`, `POST /auth/recovery/verify`, `POST /auth/recovery/reset`, `POST /auth/password/change`, and a separately authorized administrator recovery endpoint. These are design notes, not routes implemented in `server.js`.

## Verification and limits

- `node tests/auth-flows.test.cjs`: format policy, authenticated-actor requirement, unavailable outcomes for all channels, generic account-independent responses, no credential/identifier payloads in events, audit isolation and logout cleanup.
- `node tests/storage.test.cjs`: existing v2/v3 migration and data-preservation regression suite.
- `tests/auth-flows.browser.cjs` (optional Playwright): login errors, password visibility, all recovery channels, disabled verification/reset steps, administrator guidance, own-account settings for owner/GM/employee, invalid/valid-format submissions, unchanged users/roles, no new secret storage or authentication/provider network requests, Arabic/English, and widths 1440/768/390.
- Existing company, task, navigation, user-management and login regressions are also exercised separately.
- **Actual expiry, attempt limits, OTP delivery, current-password verification, reset-link replay protection, durable audit and successful secure changes cannot be tested here because their backend does not exist.** The disabled interface is checked to ensure it cannot accept a stale/invalid/unverified token or claim success. Real lifecycle/security tests are required before backend activation.

With Playwright installed in a development environment, run the static app, then `ERP_DEMO_URL=http://127.0.0.1:3000 node tests/auth-flows.browser.cjs`. Set `CHROMIUM_PATH` if using an installed Chromium. Test screenshots go to `work/auth-artifacts/` and must not be committed.
