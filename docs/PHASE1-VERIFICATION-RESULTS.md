## حالات الفشل غير المعالجة

هذه محاولات SQL مباشرة بدور تشغيل الخادم، داخل مجموعة اصطناعية؛ تم ROLLBACK لكل محاولة. ليست دليلاً على أن مستخدماً عادياً يستطيع الوصول إلى SQL أو تجاوز API. لكنها تكشف حدود حماية المخطط أمام أخطاء Backend أو مسار إدخال مستقبلي، ولذلك تمنع اعتماد المخطط سليماً بالكامل.

| المعرف | المتوقع مقابل الفعلي | السبب / المعالجة المقترحة للمراجعة |
| --- | --- | --- |
| F01 | رفض شركة لها `area_id` مع `emirate_id=NULL`؛ تم القبول | FK المركب يسمح بتجاوز الفحص عند NULL. إضافة قيد صريح: وجود المنطقة يستلزم وجود الإمارة، دون فرض موقع على شركة بلا موقع. |
| F02 | رفض alias منطقة يستخدم إمارة أخرى؛ تم القبول | FK يطابق المجموعة والمنطقة فقط. يلزم FK مركب يربط المجموعة والإمارة والمنطقة معاً. |
| F03 | رفض حساب `Closed` بلا `closed_on`؛ تم القبول | تعبير CHECK ينتج NULL، وPostgreSQL يقبله. يلزم اشتراط التاريخ غير الفارغ عند الإغلاق صراحةً. API رفض الحالة نفسها بـ422 في الاختبار. |
| F04 | رفض مستند مرتبط بمستند لشركة أخرى داخل المجموعة؛ تم القبول | FK يضمن المجموعة فقط. يلزم تحقق قاعدة بيانات من تطابق مالك المستند، مع الاحتفاظ بالعلاقات الصحيحة بين الأصل والملاحق. API رفض إصداراً مرتبطاً بمالك آخر بـ422. |
| F05 | رفض إصدار أب تابع لمستند شركة أخرى؛ تم القبول | FK الإصدار الأب يضمن المجموعة فقط. يلزم تحقق يطابق المالك والعلاقة المنطقية، مع السماح بالربط الصحيح لملاحق مستندات مختلفة للمالك نفسه. لا يجوز فرض أن كل parent ينتمي إلى المستند نفسه، لأن ذلك يلغي وظيفة الملاحق. |
| F06 | رفض INSERT لمستخدم `manager_id=id`؛ تم القبول | trigger يبحث في الصفوف قبل وجود الصف الجديد. يلزم فحص ذاتي صريح مع الإبقاء على فحص الدورات الحالي. |

التصحيح المقترح يكون **Migration لاحقاً مستقلاً** مع فحص البيانات الموجودة أولاً. إذا وُجدت سجلات غير متسقة، تُعرض للمعالجة ولا تُحذف أو يُعاد ربطها تلقائياً. يمكن تجهيز القيود NOT VALID عند انطباقها ثم VALIDATE بعد معالجة معتمدة، مع اختبارات للتوافق وعدم فقد البيانات. لم يُنفذ هذا التصحيح ضمن مرحلة التحقق الحالية.

## النسخ الاحتياطي والاستعادة

نجح اختبار الاستعادة الموسع إلى قاعدة جديدة دون استبدال المصدر:

- إنشاء شركة وحسابين بنكيين برصيد عشري دقيق وبيانات مدير الحساب، ومستخدم ببيانات شخصية مشفرة وعضوية وتفويض، ونسختين متتابعتين لمستند.
- أخذ `pg_dump` فعلي وأرشيف مشفر بمفتاح Backup مستقل ونسخ كائنات مشفرة.
- استعادة بـ`pg_restore` إلى قاعدة جديدة، ثم مطابقة بصمات **كل صفوف جداول ab عدا الجلسات** قبل أي نشاط API مستعاد. الجلسات تُنهى عمداً ولا تُعاد كجلسات فعالة.
- إثبات استرجاع بيانات الحسابين والمدير والرصيد دون تقريبه، وتنزيل النسختين الأصلية واللاحقة بالبايتات المتوقعة، مع رفض القراءة خارج سياق المجموعة والحذف.
- رفض مفتاح Backup خاطئ ومفتاح بيانات خاطئ، ورفض الأرشيف بعد العبث به ورفض تقديم ملف بعد العبث بكائنه.

أول تشغيل للاختبار الموسع رفض IBAN وهمياً غير صحيح؛ صُححت بيانات الاختبار فقط، وبقي التحقق من IBAN كما هو، ونجح التشغيل النهائي. هذا منفصل عن فجوات القيود الست التي ما زالت تفشل.

**لا يثبت ذلك تعافياً سحابياً كاملاً:** الاختبار على خادم PostgreSQL نفسه، حيث أدوار SQL موجودة مسبقاً؛ لا يثبت إعادة إنشاء الأدوار على خادم مستقل. Auth وStorage بديلان اختباريان، ولا يوجد اختبار لاستعادة Supabase Auth فعلي أو bucket أو نسخة offsite. لا يوجد scheduler أو retention أو قياس RPO/RTO أو حل متزامن لالتقاط snapshot قاعدة البيانات والكائنات. أداة الأرشفة الحالية ذاكرية وتجريبية. يلزم حفظ المفاتيح مستقلة؛ فقد مفتاح البيانات يجعل الملفات والحسابات غير قابلة للفك حتى مع وجود نسخة سليمة.

## حدود التدقيق والأمان التي تبقى واضحة

- ضمان append-only خاص بدور التشغيل، وليس حماية من مسؤول قاعدة البيانات أو دليلاً جنائياً خارجياً محصناً.
- التدقيق التجاري يضيفه API ضمن المعاملة؛ لا توجد triggers تسجل كل SQL مباشر. بيانات actor_id وحقول الأحداث تأتي من الخادم الموثوق. لا تُمنح اتصالات SQL مباشرة للمستخدمين.
- فشل تسجيل الدخول والأحداث المرفوضة لا تُسجل حالياً في سجل أمني مستقل؛ يلزم إعداد آلية مراقبة/تسجيل دون أسرار قبل التشغيل الحقيقي. لا يُدّعى أنها مكتملة.
- حماية TLS للويب لا تنتقل تلقائياً إلى CLI الترحيل/التهيئة؛ يجب فرض verified TLS صراحةً على تلك الاتصالات في إعداد Supabase المستقبلي.
- لا تغيير كلمة مرور أو OTP أو SMS/Email/WhatsApp فعلي، ولا تحقق ملكية اتصال، ولا reconciliation تلقائي لحساب Auth أو كائن يتيم عند فشل المعاملة الأخرى.

## ما يحتاج تدخلك أو موافقتك

1. مراجعة هذه النتائج واعتماد نطاق تصحيح القيود الست بترحيل لاحق دون تعديل الملفات السابقة أو الأدوار. لا ننتقل تلقائياً إلى تلك المرحلة.
2. موافقة منفصلة على مشروع Supabase Free تجريبي محدد وprivate bucket ومنطقة الاستضافة، أو تحديد مشروع موجود ومسموح للاختبار. لم تُطلب أو تُنشأ موارد مدفوعة.
3. تهيئة الأسرار عبر وسيلة محمية واعتماد وجهات HTTP/TCP الدقيقة؛ لا ترسل كلمات المرور أو المفاتيح في المحادثة.
4. اعتماد خطة الاختبار السحابي واستعادة مستقلة قبل تنفيذ عملياتها. الخطوات والمصفوفة والأوامر في [دليل ربط Supabase والتحقق](SUPABASE-VERIFICATION-RUNBOOK.md).

يبقى #10 و#11 دون دمج ونشر. نجاح الاختبارات المحلية لا يعني أن أي وظيفة أصبحت منشورة أو أن الاتصال الحقيقي قد اختُبر.

## تحديث تنفيذي — إصلاح الحالات الست بعد موافقة المالك

نُفّذت الإصلاحات بملف جديد `202611020008_schema_integrity.sql`، دون تغيير أي من الملفات السبعة السابقة أو الأدوار أو وظائف الواجهة. أضيفت قيود الإمارة/المنطقة وتاريخ الإغلاق والمسؤول الذاتي، وFK لمرجع المنطقة، وtriggers لعلاقات مالكي المستندات وإصداراتها مع الإبقاء على الملاحق الصحيحة. يتحقق الترحيل من البيانات السابقة ويتراجع كاملاً عند وجود مخالفة؛ لا إصلاح صامت أو حذف.

- مراجعة المخطط بعد التصحيح: **29 ناجحة، صفر فاشلة**، بما فيها الحالات الست الأصلية. النتائج: `verification/schema-review-2026-11-02-fixed.json`. الملف السابق ذو النتائج الفاشلة محفوظ كسجل تاريخي.
- حزمة Backend: **6 سيناريوهات ناجحة**، ومنها اختبار جديد لترقية v7 إلى v8، وإثبات رفض البيانات القديمة غير المتسقة دون فقدها أو تسجيل ترحيل جزئي، ثم نجاح الترحيل بعد تصحيح صريح لبيانات fixture الاصطناعية فقط.
- اختبارات المنطق/التخزين القديمة في الملفات الثمانية ناجحة. الاستعادة الموسعة والحسابات والمدير والمستخدم والتفويض والملاحق والإصدارات ما زالت ناجحة.
- الخطوة العملية التالية متوقفة فقط على مشروع Supabase التجريبي والأسرار وإتاحة الاتصال؛ لا موارد أو اتصال سحابي فعلي أو نشر أُنشئ. [خطوات المالك المختصرة](SUPABASE-QUICKSTART-OWNER.md).

توصية التوقف السابقة كانت تصف الحالة قبل موافقة الإصلاح؛ الفجوات الست معالجة الآن. بقية متطلبات التشغيل الحقيقي واستعادة Auth السحابية وفحص الملفات ما زالت كما هي. لا حاجة إلى موافقة أخرى لإعادة المراجعة المحلية؛ نكمل الربط عند تجهيز المشروع والأسرار.

نجح أيضاً اختبار متصفح الواجهة المركزية بعد الترحيل 008: الدخول وإنشاء/تعديل الشركة والبنك ومديره والمستخدم والمستند وإعادة الفتح، بالعربية والإنجليزية وعلى الهاتف، دون أخطاء JavaScript أو استخدام المخازن الحساسة للمتصفح. يظل مزود Auth/Storage في هذا الاختبار بديلاً اختبارياً، وليس Supabase الفعلي.

## تحديث توافق مفاتيح Supabase الجديدة

أبلغ المالك بإنشاء مشروع Free وbucket خاص. أُضيف دعم المتغيرين SUPABASE_PUBLISHABLE_KEY وSUPABASE_SECRET_KEY مع التوافق القديم، وفصل ترويسة apikey عن رمز المستخدم في Authorization. اختُبر عقد REST للمفاتيح الجديدة والقديمة محلياً، مع رفض تعارض القيم وعكس مستوى المفتاح. اتصالات PostgreSQL للخادم وأدوات الإدارة والفحص تستخدم الآن التحقق الموحد من TLS. ملف إدخال الأسرار خارج المستودع وبصلاحية 600، ولا يحتوي في وقت التجهيز بيانات اتصال. فحص الاتصال الجديد أعاد NOT_RUN/exit 2 قبل الشبكة لغياب القيم؛ لم يُطبّق الترحيل على Supabase الفعلي بعد. [الخطوات اليدوية الحالية فقط](SUPABASE-QUICKSTART-OWNER.md).
