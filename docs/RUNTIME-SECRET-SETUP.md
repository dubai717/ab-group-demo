# تهيئة ab_runtime — الإجراء اليدوي المطلوب فقط

وافق المالك على تعيين كلمة مرور مستقلة للدور الموجود `ab_runtime`، دون أدوار أو GRANTs جديدة ودون تغيير RLS. التنفيذ مُجهّز في `.github/workflows/supabase-runtime.yml`، ولم يُطلق بعد لأن كلمة المرور يجب حفظها أولاً في GitHub Secrets، لا توليدها ثم فقدها أو عرضها في السجلات.

## أضف السرّين داخل Environment الحالية supabase-test

**GitHub → Settings → Environments → supabase-test → Environment secrets**.

1. **DATABASE_URL**: رابط اتصال مستقل بنفس مضيف Session pooler والمنفذ 5432 وقاعدة postgres الموجودين في الاتصال الناجح، لكن باسم مستخدم `ab_runtime.<PROJECT_REF>` وكلمة مرور جديدة قوية مستقلة. لا تغيّر MIGRATION_DATABASE_URL ولا تعِد تعيين كلمة مرور postgres. مثال صيغة فقط، دون قيم فعلية:

```text
postgresql://ab_runtime.<PROJECT_REF>:<NEW_RUNTIME_PASSWORD>@<SESSION_POOLER_HOST>:5432/postgres?sslmode=verify-full
```

لتجنب مشكلات الترميز، ولّد كلمة المرور الجديدة **على جهازك الموثوق** بالأمر `openssl rand -hex 32` واستخدم الناتج كما هو في خانة NEW_RUNTIME_PASSWORD. الناتج 64 محرفاً سداسياً عشوائياً لا تحتاج ترميز URI إضافياً. لا تنسخ كلمة مرور الإدارة أو مفتاح API؛ لا ترسل الناتج في المحادثة. لم تُعيّن هذه الكلمة في قاعدة البيانات بعد؛ الـworkflow سيعيّنها للدور القائم من السر المحفوظ.

2. **DATA_ENCRYPTION_KEY**، إذا لم يكن موجوداً بالفعل: قيمة Base64 لـ32 بايت عشوائية، تُولّد مستقلة على جهازك بالأمر `openssl rand -base64 32`. انسخ الناتج إلى GitHub فقط. إذا أضفته سابقاً فأبقِه كما هو؛ لا تستبدله عشوائياً. احتفظ بنسخة محمية مستقلة لدى مالك المشروع؛ فقده يمنع قراءة البيانات والملفات المشفرة حتى مع وجود نسخة من قاعدة البيانات.

لا تضع القيم في ملفات المستودع أو backend.env أو Variables أو المحادثة. إذا لم يتوفر openssl على جهازك، أخبرني بنظام الجهاز فقط، دون إرسال أسرار. بعد الحفظ قل: **«تم تجهيز DATABASE_URL وDATA_ENCRYPTION_KEY»**.

## ما سيُنفّذ تلقائياً بعد ذلك

سأدفع فرع `verify/supabase-test-runtime-approved-20261102` من المصدر المختبر. إذا كان Environment يتطلب مراجعة، وافق على تشغيل هذا الفرع فقط. لا تعديل لـmain أو Pages، ولا دمج #10/#11 أو نشر.

- يتحقق العمل الأول من مطابقة المشروع والمضيف والمستخدم، وقوة واستقلال كلمة المرور، ويرفض تجاوزات URI. يتصل إدارياً فقط لتعيين كلمة مرور `ab_runtime` الموجود بصيغة SCRAM مشتقة على العميل؛ كلمة المرور المكشوفة لا توضع في SQL. لا كلمة المرور أو verifier تُطبع في سجلات GitHub.
- يأخذ بصمة داخلية لخصائص الدور وعضوياته وحقوق الجداول وسياسات RLS قبل العملية وبعدها. التغيير الوحيد المسموح هو كلمة المرور؛ أي تغير آخر يُفشل المعاملة ويوقف العمل. لا إنشاء دور، لا GRANT/REVOKE، ولا تهيئة/ترحيل مخطط جديد.
- يغلق اتصال الإدارة، ثم يصادق اتصال DATABASE_URL مستقلاً. يتحقق من TLS و`current_user=session_user=ab_runtime` ومن منع قراءة خارج نطاق المجموعة ومن غياب DELETE/TRUNCATE وتعديل مستندات/تدقيق قديمة. لا SET ROLE.
- بعد النجاح يبدأ عمل منفصل للاختبارات الواقعية باستخدام Supabase Auth/PostgreSQL/Storage الحقيقيين. يهيئ الوالد مجموعة ومالكاً وهميين جديدين فقط، ثم يغلق الإدارة. عملية اختبار الـBackend الابنة تستقبل DATABASE_URL فقط ولا تستقبل MIGRATION_DATABASE_URL أو GITHUB_TOKEN؛ تمرر بيانات دخول fixture عبر stdin الخاص لا args أو outputs أو ملف.
- تشمل الاختبارات الدخول الصحيح والخاطئ، حفظ/إعادة فتح الشركة وسالك/الرمز المروري، حسابين للشركة ورصيداً دقيقاً ومدير حساب، مستخدماً وهمياً وصلاحياته، RLS الفعلي بعد وجود سجلات، رفع مستند مشفر، ورفض قراءة الكائن للعامة والمستخدم غير المخوّل.
- المستند يظل pending ومحجوراً لأن فاحصاً حقيقياً لم يُجهّز؛ لا يوضع عليه clean وهمي. لا اختبار تنزيل مصرح نظيف قبل الفحص الحقيقي.
- تبقى السجلات والحسابات والملفات الوهمية محفوظة؛ لا cleanup أو حذف تلقائي. كلمات مرور حسابات الاختبار الآلية عشوائية ومؤقتة في ذاكرة runner، ولا تُعرض أو تُستخدم كحسابات موظفين حقيقيين. مفتاح تشفير السجلات المحفوظة دائم في Environment.

لا يُعد هذا نشر واجهة تفاعلية أو اختبار استعادة سحابية. التشغيل الفعلي عبر الواجهة يحتاج لاحقاً جهازاً/بيئة Backend موثوقة ومحمية؛ صفحة GitHub Pages العامة لا تتلقى الأسرار. لا تُنشأ خدمات مدفوعة.

## التحقق التحضيري

نجحت تسعة اختبارات جديدة محلياً: فصل الاتصال وقوة الكلمة، شكل SCRAM وعدم احتوائه على النص، عزل الإدارة عن عملية التطبيق، منع التشغيل غير المخوّل دون تسريب، مصادقة PostgreSQL فعلية محلية بالـSCRAM الجديد مع ثبات الصلاحيات، الحفاظ على 367 منطقة ومرجع البنك عند تسريع إدخال fixture، وعدم تصدير الأسرار إلى outputs/artifacts، والتوقف قبل إنشاء البيانات عند غياب مفتاح دائم، ورفض تمرير الإدارة إلى العملية الابنة. TypeScript وactionlint ناجحان. لا ندّعي أن تهيئة الكلمة السحابية أو اختبارات ERP الفعلية أُنجزت قبل توفر السرّين وتشغيل workflow.
