# الوضع الحالي: فحص Supabase للقراءة فقط

بحسب طلب المالك الأخير، workflow الحالي لا يطبق Migrations أو يعدّل بيانات/مخططاً. يجري فحص اتصال TLS والمفاتيح والـbucket الخاص، ثم يقرأ حالة المخطط إن كان موجوداً ويقارن checksums الترحيلات وصلاحيات RLS. إذا لم يُطبّق المخطط يُعرض NOT_APPLIED دون إنشائه. حُذفت إعادة حزم الاختبارات المحلية من هذا التشغيل لتجنب تكرار ما نجح سابقاً؛ ملفات الاختبارات نفسها محفوظة.

فرع التحقق: `verify/supabase-test-readonly-20261102`. عند ظهور Waiting/Review deployments، افتح التشغيل واعتمد البيئة `supabase-test` لهذا الفرع فقط. هذه موافقة لإتاحة Secrets لفحص القراءة، وليست نشر موقع أو إذناً لتعديل قاعدة البيانات. لا تعدّل Secrets أو ترسل قيمها.

التغيير اختُبر فقط في مسارات القراءة الجديدة وفُحص بـTypeScript وactionlint. النص السابق أدناه توثيق تاريخي لخطة الترحيل التلقائي التي لا ينفذها workflow الحالي.

# اختبار Supabase عبر GitHub Actions فقط

هذه الآلية تستخدم GitHub Actions Environments/Secrets والـSupabase Free الموجودين؛ لا مدير أسرار إضافي، ولا نشر موقع، ولا دمج #10/#11، ولا وصول للأسرار من مساحة العمل الحالية. المستودع عام، والعمل يستخدم runner قياسياً `ubuntu-latest`، لا runner ذاتياً أو مدفوعاً/كبيراً.

## الخطوة اليدوية التالية فقط

من مستودع `dubai717/ab-group-demo` في GitHub:

**Settings → Environments → New environment → `supabase-test`**

في البيئة نفسها:

1. فعّل **Required reviewers** واختر حسابك. اترك **Prevent self-review** مغلقاً إذا كنت المراجع الوحيد، حتى تستطيع اعتماد التشغيل الذي يبدأ باسمك. لا تغيّر إعدادات Pages أو استضافة الموقع.
2. ضمن **Deployment branches and tags** اختر **Selected branches and tags**، وأضف قاعدة **Branch** بالنمط `verify/supabase-test-*`. هذا قيد وصول لأسرار الاختبار؛ ليس تفعيل نشر موقع.
3. أضف **Environment secrets** الأربعة، وليست Variables ولا ملفاً في المستودع:

| الاسم | القيمة |
| --- | --- |
| `SUPABASE_URL` | رابط مشروع `ab-group-erp-test` |
| `SUPABASE_PUBLISHABLE_KEY` | مفتاح `sb_publishable_...` الجديد |
| `SUPABASE_SECRET_KEY` | مفتاح `sb_secret_...` الجديد، للخادم فقط |
| `MIGRATION_DATABASE_URL` | رابط PostgreSQL الإداري من Supabase **Connect → Session pooler، 5432** مع كلمة مرور قاعدة البيانات. حافظ على التحقق من TLS؛ إذا أضاف الرابط `sslmode` فيجب أن يكون `verify-full`. لا تستخدم Transaction pooler أو رابطاً لمشروع تشغيل حقيقي. |

URI-encode كلمة مرور قاعدة البيانات إذا كانت تحتوي رموزاً خاصة عند تركيب الرابط. أدخل القيم مباشرة في واجهة GitHub؛ لا ترسلها في المحادثة أو صور أو ملفات. لا تستخدم ملف `backend.env` في مساحة العمل غير الموثوقة. لا تضف أسراراً على مستوى Repository إذا كنت تستخدم هذه البيئة المحمية.

بعد الإعداد، أخبرني فقط: **«جهزت بيئة supabase-test والأسرار الأربعة»**. لا ترسل القيم. إعداد البيئة أعلاه هو المطلوب الآن؛ لن نطلب منك تعديل الكود أو main أو شراء خدمة.

## ما يحدث بعدها

- سأدفع فرع تحقق محدداً `verify/supabase-test-<revision>` من نسخة فرع الإصلاح المختبرة، دون تغيير main أو فرع التكامل. هذا هو trigger التشغيل، لأن `workflow_dispatch` غير متاح عادةً قبل وجود ملف workflow على الفرع الافتراضي، ولا نريد الدمج لأجل ذلك.
- تجري الاختبارات المحلية أولاً على runner بلا أسرار Supabase. ثم يظهر طلب موافقتك في GitHub للبيئة `supabase-test`. وافق فقط على تشغيل فرع التحقق والـcommit المعلن؛ بعد الموافقة تُحقن الأسرار في خطوة الفحص المحددة فقط.
- لا توجد حاجة إلى نقل الأسرار إلى ChatGPT أو مساحة العمل. سأقرأ نتائج الحالة المنقحة من GitHub، لا إعدادات الأسرار أو قيمها.

## النطاق الفعلي للتشغيل الأول

1. اتصال PostgreSQL موثّق TLS؛ تطابق مشروع الاتصال مع رابط Supabase؛ اختبار مفاتيح Publishable/Secret الفعلية، ووجود الـbucket الخاص `ab-private-test`، وعدم وجود سياسات مباشرة تتيح ملفاته للعامة أو المستخدمين.
2. تطبيق **Migrations الثمانية** على المشروع التجريبي، دون reset أو ترحيل بيانات المتصفح. الترحيل يتوقف إذا وجد بيانات قديمة غير متسقة؛ لا حذف أو إصلاح صامت.
3. تحقق RLS والدوال والقيود وحماية المالك ودور التشغيل وسجل التدقيق والمرفقات append-only، ورفض قراءة الشركات والبنوك دون سياق مجموعة.

هذه الخطوة **لا تنشئ مشروعاً أو bucket أو خدمة مدفوعة**، لكنها تنشئ كائنات مخطط SQL والأدوار المرجعية المعتمدة في مشروعك التجريبي. لا تغيّر سياسات bucket الموجودة؛ إذا اكتُشف إعداد غير آمن يفشل الاختبار بدلاً من تبديله خفية.

لا يدّعي التشغيل الأول إنشاء مستخدم Auth أو نجاح الدخول بكلمة مرور أو CRUD فعلي بهوية جديدة. بعد إثبات الاتصال/المخطط، يُستكمل تدفق البيانات الوهمية ضمن الآلية المحمية نفسها. قبل حفظ سجلات مشفرة دائمة، يلزم مفتاح بيانات ثابت ومحمي؛ لا يولّد هذا التشغيل مفتاحاً عابراً ثم يترك بيانات غير قابلة للفك. ليس هناك رابط تفاعلي عام للنظام ولا استعادة سحابية مثبتة بمجرد نجاح هذه الخطوة.

## ضوابط حماية الأسرار

- workflow في `.github/workflows/supabase-test.yml`، لا يعمل على PR أو fork أو schedule، ويرفض runner ذاتياً ومستودعاً/مساراً/حدثاً/فرعاً مختلفاً.
- `GITHUB_TOKEN` بقراءة المحتوى فقط. `checkout` لا يحتفظ ببيانات اعتماد Git. Actions الرسمية مثبتة بـSHA كامل.
- لا أسرار على مستوى job أو في checkout/تثبيت الحزم. التثبيت بـ`npm ci --ignore-scripts`، ثم تُحقن القيم في خطوة Node واحدة فقط بعد بوابة البيئة.
- لا echo للأسرار أو env dump أو shell tracing؛ لا تمريرها كوسائط أو workflow inputs أو outputs. تُستخدم process.env داخل runner المؤقت.
- تُلتقط مخرجات فحص المزود ولا تُمرر raw؛ الأخطاء والملخص يحتويان أسماء مراحل ثابتة فقط. توجد اختبارات canary بقيم وهمية تؤكد عدم تسربها في المخرجات، بالإضافة إلى حماية GitHub masking كدفاع إضافي.
- لا artifacts أو cache أو لقطات شاشة أو `.env` أو رفع ملفات بعد خطوة الأسرار. الملخص يعرض نتائج منقحة فقط. لا أي صلاحية Pages أو deployments أو طلب نشر في workflow.
- GitHub قد يُنشئ سجلاً مرتبطاً ببيئة الاختبار عند job يستخدم Environment؛ هذا لا ينشر التطبيق أو يغير Pages.
- تبقى حسابات إدارة GitHub ومراجعو البيئة والكود المعتمد ضمن نطاق الثقة. لا توجد ضمانة ضد مسؤول مستودع مخوّل يغيّر الحماية أو يوافق على كود يسرّب أسراراً؛ لذلك القيود والموافقة المسبقة ضرورية، ولا تُمنح كتابة/إدارة المستودع لغير المخولين.

## التحقق قبل إدخال أسرار

اختبارات `backend/tests/actions-isolation.test.ts` تتحقق من قيود السياق، وعدم كشف canaries، وحدود صلاحيات workflow وفصل الأسرار، وفحص المخطط على PostgreSQL محلي. نجحت حزمة Backend المحلية ذات 14 سيناريو. هذا إثبات إعداد محلي، وليس تشغيل GitHub فعلياً أو اتصال Supabase حتى إعداد الأسرار واعتماد أول job.
