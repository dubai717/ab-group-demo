# Funding review, documented disbursement and employee directory

Repository: dubai717/ab-group-demo only. Base: d5b4840. No SQL/schema migrations, financial 028 activation, permission catalog changes, bulk account changes, reset or historical balance edits.

## Root causes and canonical review

The original vehicle UI marked `reason` required in the shared approval checkbox form; the original API also required a nonempty reason for both boolean outcomes. Separate approve/reject/return forms now use an explicit decision enum. Approval has an optional note. A predefined rejection code is required for the new rejection form; Other needs details. Return requires a correction note. The legacy boolean API remains accepted with the corrected approval semantics. Prior decisions remain unchanged.

The original summary/list did not carry enough saved request detail. A scoped request GET now reads the stored definition, actual customer/file, company, creator, original financial figures, separate fee quotes, linked original customer archive files and immutable decision history. All entry points, including notifications and the existing approval center, open this canonical review with a current revision. The approval center no longer sends funding through its generic mandatory-reason prompt. Decisions lock the request, compare its revision and append history. Returned requests need a saved correction before approval; return creates an existing personnel task when the original creator has an eligible staff record, and an authorized existing notification. No fake staff or permissions are created to satisfy assignment.

All new public API requests receive review policy version 1 on the server; omission cannot downgrade a new request. Internal sales also create fresh review proposals. Historical imports and stored agreements are preserved. Legacy compatibility tests explicitly seed historical encrypted request/event fixtures into guarded, random local databases; they do not expose a production legacy switch or pretend that today's API creates old-policy records. The private TEST_DATA compatibility generator also explicitly seeds historical fictional proposals; it does not relax the public creation API. Existing undecided financing still requires the evaluation fields before a new approval. New reviewed agreements lock the approved principal, repayment total, term and monthly registration fee.

## Financial and registration sequence

The old receiver list showed active users without filtering their receiving permission, although the server rejected unqualified receivers. Cheque/transfer proof was an unrestricted UUID input. New disbursement options use actual scoped active bank accounts, eligible receiving users and already approved matching payments. The selected operation determines bank/source/date. Optional PRO assignment uses the existing employee/task rules. Missing staff assignment stays visible and can be completed through the original PRO task action; it does not fabricate an employee or grant access.

Saving a disbursement links existing actual financial evidence, never posts a second payment. For cash, only an actual active cash fund and an existing approved principal-asset/cash journal qualify, with nonnegative fund balance, clean existing evidence and explicit actual handover confirmation. A request/journal lock and immutable source event prevent reuse. A linked cash proof cannot be reversed through the ordinary manual reversal action; a formal funding correction is required. Investor acceptance/capital/bank-disbursement guards remain in force, and investor cash is not offered.

The original registration emirate selector referenced a nonexistent ABCentral.emirates property. It now uses the same reviewed UAE reference as the rest of the application. New registration opens after approved funding, documented payment and receiver acknowledgment, prefilling the saved vehicle data. New records remain Pending until scoped activation verifies technical identity, emirate, registration/ownership/insurance dates and clean ownership/insurance files. Existing registered vehicles and subsequent sale/status workflows retain their original paths. The canonical registration task's completion checks actual activation on new records.

Customer schedules use exact decimal arithmetic and the approved terms. Down payment is stored separately from the financed installment total, is never deducted twice and never creates an automatic receipt. The last installment settles the remaining rounding difference. Principal totals below financing, stale decisions, term/fee changes and duplicate contracts/invoices are rejected. Recurring registration fees keep their existing separate source. Independent one-off fee quotes are shown separately; they are not silently treated as collected cash or auto-posted without the existing explicit invoicing procedure.

## Bank/company and company/customer agreements

New bank funding requires approval and has an independent bank contract identity/number and immutable approval snapshot. The bank's borrower is the group company, never the customer. Its principal, total, months, installment, fees and due schedule can differ from the company/customer financing. The customer agreement stores its own schedule and the bank agreement snapshot; old external-bank records are not reinterpreted.

The bank contract view shows separate contractual and actual figures. Authorized operators explicitly link already approved native financial operations: loan drawdown and principal repayment must use an approved liability classification; actual interest/fees must use expense classification. Source reuse, cross-company/currency/bank access, investor capital/client receipt reuse, excess principal/costs and overallocated installments are blocked. Linking appends a relation; it creates no operation, journal or cheque. Actual loan balance and bank cash flow are distinct from scheduled totals. Original company ledger/profit/cash-flow reports remain the accounting source; capital is never labeled income and contractual spread is labeled a forecast rather than realized profit. No assumed amortization split or automatic bank accounting mapping is installed.

## Personnel and units

Personnel → Administrative units reuses ab.departments with supplemental descriptive metadata in existing settings. Owner-only create/edit/disable supports Arabic/English name, code, description, manager, status and company. Duplicate checks also cover the original departments creation path. Disable does not delete staff links or change inherited permissions. Employee creation shows eligible active units for the selected company, and inline Add unit updates that select without losing entered employee data. An unchanged inactive historical unit is retained on ordinary profile edits.

Employee profiles are primary. A profile can open the original user editor with permitted basic data prefilled; role/scope and credentials still require the original explicit owner procedure. A return control leads back to the employee. Existing active login linking requires explicit owner confirmation, company eligibility, revision and uniqueness; links cannot be replaced. Only permitted ERP display/contact/job fields synchronize on explicit staff edits/linking. Username, authentication email, provider password, role, membership scopes and grants are not modified by synchronization. The retained legacy create-with-userId API preserves its original account-name aliases; the new UI is employee-first and performs synchronization only through explicit confirmed linking or profile editing. Independent owner/nonstaff accounts remain available.

Identity/marital data remains in the restricted encrypted employee payload. Emirates ID has syntax/Luhn checks and a serialized duplicate check. UAE mobile input accepts local/international separators and normalizes for display; foreign country numbers retain their country code without imposing a UAE format. Employee numbers use the existing atomic sequence. Forms show examples and grouped headings. Successful create closes the form and shows the saved register row.

Multiple PDF/JPG/PNG files use original durable encrypted storage, scanning, categories and version APIs, with stable per-file retry keys. Original attachments are preserved. Images and PDFs use the shared authorized preview/download viewer. Front/back ID pairs count toward the existing identity requirement only after both are clean and approved; optional expired documents do not reduce mandatory completeness.
