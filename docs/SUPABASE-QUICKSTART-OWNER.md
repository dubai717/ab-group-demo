# Supabase التجريبي — إدخال الاتصال فقط

المشروع `ab-group-erp-test` والـBucket الخاص `ab-private-test` أُنشئا بالفعل بواسطة المالك. **لا تعِد إنشاءهما ولا تحتاج إلى مفاتيح Legacy أو خدمة مدفوعة.** Backend يدعم الآن `sb_publishable_...` و`sb_secret_...`، مع الإبقاء على الأسماء القديمة للتوافق.

## المطلوب منك

افتح **في محرر بيئة العمل الخاصة فقط** الملف:

`/workspace/.ab-group-erp-test/backend.env`

هذا الملف خارج مستودع Git وخارج ملفات العرض؛ المجلد بصلاحية 700 والملف 600. جُهّز فارغاً ولا يحتوي أسراراً حالياً. لا ترفعه أو تنسخه للمحادثة أو GitHub/Pages. املأ الحقول الأربعة الأولى مباشرة:

| المتغير | القيمة ومكان الحصول عليها |
| --- | --- |
| `SUPABASE_URL` | رابط المشروع `https://<project-ref>.supabase.co` من Connect/إعدادات المشروع. |
| `SUPABASE_PUBLISHABLE_KEY` | مفتاح Publishable الجديد الذي يبدأ بـ`sb_publishable_`. |
| `SUPABASE_SECRET_KEY` | مفتاح Secret الجديد الذي يبدأ بـ`sb_secret_`، للخادم فقط. |
| `MIGRATION_DATABASE_URL` | رابط PostgreSQL الإداري من **Connect** مع كلمة مرور قاعدة البيانات، وليس مفتاح API. اختر Direct إن كان متاحاً، أو **Session pooler على 5432**، وليس Transaction pooler. استخدم TLS موثقاً (`sslmode=verify-full` أو تحقق الشهادة الافتراضي للأداة). URI-encode كلمة المرور إذا احتوت رموزاً خاصة. |

لا تملأ `DATABASE_URL` أو مفاتيح التشفير يدوياً؛ سأجهّز دور التشغيل المحدود والمفاتيح منفصلة بعد الاتصال. لا تستخدم اتصال postgres الإداري لتشغيل الويب.

إذا كانت واجهة بيئة العمل توفر **Secrets/Environment variables** محمية، يمكن إدخال القيم هناك بالأسماء نفسها بدلاً من الملف. لا أملك أداة لإضافة أسرارك إلى تلك الواجهة نيابةً عنك. إذا لم تجد محرر الملفات أو مكان الأسرار، أخبرني بذلك فقط، دون إرسال أي قيمة سرية.

في إعدادات شبكة بيئة العمل، يلزم السماح لـHTTPS لمضيف المشروع، وTCP لمضيف قاعدة البيانات على 5432؛ لا تعطل التحقق من TLS ولا تحاول تجاوز proxy. يمكنني تحديد المضيفين غير السريين من الإعداد بعد إدخاله. أخبرني فقط: **«تم إدخال القيم»**، ثم أستكمل ما تسمح به الشبكة. إذا طلبت واجهة الشبكة منك أسماء الوجهات، استخدم مضيف رابط المشروع ومضيف رابط قاعدة البيانات دون اسم مستخدم أو كلمة مرور.

## ما سأنفذه بعد الإدخال

1. فحص SQL/TLS الفعلي، وصلاحية مفاتيح API، ووجود bucket خاص دون سياسات قراءة/كتابة مباشرة للعامة أو المستخدمين.
2. تطبيق Migrations الثمانية الحالية، وفحص RLS والدوال والصلاحيات، وتكوين دور SQL محدود للتطبيق. لا حذف أو استبدال بيانات أو سياسات موجودة دون معالجة صريحة.
3. تهيئة مالك وهمي ثم اختبار الدخول وإنشاء الشركة والحساب البنكي ومديره والمستخدم والمرفقات؛ الحفظ لا يُعرض ناجحاً قبل نجاح قاعدة البيانات.
4. الإبقاء على #10 و#11 دون دمج أو نشر. المستندات تظل محجورة دون فاحص فعلي، ولا يُحاكى نجاح OTP أو استعادة كلمة مرور.

فحص الاتصال الجاهز لا يغيّر المشروع ولا ينشئ موارد:

```sh
node --env-file=/workspace/.ab-group-erp-test/backend.env --import tsx backend/review/connection-check.ts
```

عند غياب القيم يرجع NOT_RUN/exit 2 قبل أي شبكة. نجاحه يثبت الاتصال والإعدادات فقط؛ لا يثبت تلقائياً حفظ ERP أو استعادة سحابية. عند فشل اتصال لا يطبع الأداة كلمات المرور أو ردود المزود الحساسة.

## توافق المفاتيح

المفاتيح الجديدة تُرسل في `apikey` فقط؛ `Authorization: Bearer` مخصص لرمز جلسة المستخدم الفعلي في التحقق والخروج. مفاتيح Legacy تحتفظ بسلوكها السابق. يدعم الخادم والمهاجر وعامل الفحص TLS موثقاً للاتصالات البعيدة. متغيرا Legacy الاختياريان `SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` يعملان؛ اتركهما فارغين عند استخدام المتغيرات الجديدة، وتُرفض القيم المتعارضة أو وضع Secret مكان Publishable.

المصدر الرسمي: [Supabase API keys](https://supabase.com/docs/guides/api/api-keys)، والمصدر المراجع في المستودع الرسمي: [getting-started/api-keys.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/getting-started/api-keys.mdx).

هذه البيئة التجريبية ليست مخزناً دائماً للمفاتيح؛ احتفظ بنسخة مستقلة في مدير أسرارك. لا بيانات تشغيل حقيقية حالياً.
