# نطاق عرض المستخدمين وإسناد الشركات — غير منشور

المرجع: 3.1–3.3. لا يغلق هذا الإصلاح مطلب المنع الفردي الموروث أو النطاق الجغرافي أو جميع سياسات قاعدة البيانات داخل الشركة.

## سبب العيوب المثبتة في الاختبار المعزول

- كان `view_users` في أي ستاندرد مخصص يعامل كعرض عام؛ وصلت أسماء حسابات شركة ثانية في bootstrap رغم أن العضوية الفعلية لشركة واحدة. لا يثبت ذلك حدوث وصول غير مشروع على التشغيل.
- كان فحص الإسناد يقبل وجود شركة مشتركة فقط، لذلك أمكن الاحتفاظ بالشركة المسموحة وإضافة أخرى. أعاد PATCH فعلي 200 بدلاً من403 في قاعدة اصطناعية قبل الإصلاح.
- كانت إحصاءات المستخدمين تحسب جميع حسابات المؤسسة قبل تصفية العرض.
- كان مسار التعديل يصل إلى فحص النسخة والبيانات الخاصة قبل تحقق صريح من صلاحية تعديل الهدف؛ أصبح يتحقق أولاً، بما فيه طلب بلا تغيير.

## المعالجة داخل النظام الموجود

`user-management.js` هو مصدر السياسة المشترك القائم. الستاندرد المخصص يورث عرض دليل المستخدمين عبر عضوية الشركات الفعلية، مع بقاء عرض الذات والاستثناءات الفردية الصريحة وحماية حساب المالك. لم تتغير الأدوار القديمة المدمجة ضمن هذا الإصلاح.

تغيير شركات/وحدات مستخدم ذي ستاندرد مخصص يخضع للمالك؛ الإسناد العام لا يوسع صلاحية الموظف عبر عضويته. بالنسبة إلى إنشاء المستخدمين وبقية تغييرات العضوية، تتحقق السياسة من كل شركة مضافة أو محذوفة ومن شركة كل وحدة؛ لا يكفي تطابق شركة واحدة. تعرض حقول النطاق المقفلة كقراءة فقط، وتظل الحقول الوظيفية المصرح بها مستقلة.

مسار الحفظ الأصلي يتحقق من عرض الهدف وأحد أذونات التعديل/الإسناد/الحالة قبل قراءة البيانات الخاصة أو فحص النسخة. تستخدم العدادات نفس القائمة المرئية.

حتى لا تُحجب استثناءات المالك عند تحميل دليل محدود، يرسل bootstrap مراجع دنيا للمنح الصريحة ذات الصلة بإدارة المستخدمين: اسم الشركة ومعرفها فقط، وعلاقات الإشراف اللازمة كمعرفات دون بيانات حساب. تستهلكها سياسة الواجهة الموجودة؛ لا تتحول إلى حسابات، ولا تمنح عرض ملف الشركة أو مستنداتها، ولا تدخل دليل الشركات التشغيلي. يبقى الخادم صاحب قرار التنفيذ ويعيد التحقق عند كل إجراء.

## الإثبات القابل للتكرار

- `node --test tests/managed-user-visibility.test.cjs`: العرض والذات والاستثناء وسحبه، غياب الشركة الفعلية، منع توسيع النطاق، ومراجع الإشراف دون اختراع حسابات.
- `node --import tsx --test --test-concurrency=1 backend/tests/managed-user-visibility.test.ts`: مسارات HTTP الأصلية وحسابات اصطناعية؛ رفض توسيع الذات/الغير وهدف خارج النطاق، عدادات متطابقة، ثبات المستخدمين والعضويات والمنح أثناء القراءات والرفض، ثم بقاء استثناء الشركة الصريح قابلاً للاستخدام.
- `backend/tests/managed-user-visibility.browser.cjs` ضمن مجموعة النسخة التشغيلية: الصف يفتح الملف، عرض نطاق مقفل، استثناء الشركة والإشراف رغم عدم عرض حساب الجذر، أسماء شركات مفهومة، العربية والإنجليزية وثلاثة أحجام.

النسخ السابقة الفاشلة محفوظة كأدلة تشخيص محلية. فشل المحاولة الأولى للمتصفح بسبب محاولة نقر زر فتح مخفي؛ صحح الاختبار لينقر الصف الذي يفتحه النظام فعلياً، دون تعديل سلوك المنتج لهذا الغرض. لا ترحيل أو تعديل بيانات فعلية أو صلاحيات تشغيل أو دمج أو نشر.

## التحقق من مسؤول الإشراف المقترح

أثبت اختبار سياسة مستقل أن فحص نطاق المرؤوسين كان ينظر إلى علاقة السجل القديمة عند تغيير المسؤول؛ نجح خروج من النطاق في الاختبار قبل الإصلاح. أصبحت السياسة تقيّم المسؤول المقترح وسلسلة إشرافه، مع فحص الحالة السابقة أيضاً كما في مسار الحفظ الأصلي.

اختبار HTTP مستقل رفض إزالة المسؤول التي تخرج الهدف من النطاق مع ثبات السجل والنسخة، ثم قبل إعادة إسناده إلى مرؤوس مخول وأثبت القراءة اللاحقة ورقم النسخة الجديد. صححت إحدى محاولات الاختبار توقعاً خاطئاً لشكل استجابة PATCH؛ الاستجابة الأصلية لا تعيد جميع الحقول، لذلك يقرأ الاختبار bootstrap الأصلي للتحقق من النتيجة ولا يغير عقد API.

بعد هذا التعديل:187 فحصاً ثابتاً،10 حالات خادم مركزة، وبناء خالٍ من الاتصال بالمزودين نجحت. أعيدت رحلتا عرض النطاق والاستثناءات الانتقائية بالواجهة؛ تبقى الرحلات الـ19 الكاملة دليلاً على الحزمة السابقة، وليست إعادة كاملة بعد تعديل نطاق الإشراف الأخير. حالات الاختبار ليست أعداداً تراكمية مستقلة.
