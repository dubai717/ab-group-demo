# Independent backup run recovery — inactive sandbox preparation

Reuses the original AES-GCM archive/checksums, original private independent destination adapter and existing approved-cadence planner. No live entrypoint, environment lookup, scheduler, cloud resource, source connection, bucket configuration, retention deletion, reset or database restore is added. Test dumps are explicit synthetic bytes, not a claim of PostgreSQL restorability.

`independent-backup-spool.ts` accepts only explicit sandbox configuration and an already provisioned owner-only0700 directory named `ab-backup-spool-*`. Real paths, file ownership/modes and directory identity are checked; symbolic links and substituted directories refuse. Files are0600, and contain only the original encrypted archive or authenticated encrypted technical records. Backup/data keys must be independent canonical32-byte keys; keys are never written into the records. Source/destination identity hashes must differ.

Prepared archives are written to a fresh private temporary file, synced and published with a create-only hard link, then the directory is synced. Concurrent preparations retain one complete winner. The competing temporary link is removed only after publication; retained archives/receipts are never overwritten or deleted. There is no sweep of existing/unknown files or incomplete temporary artifacts. Read recovery validates authenticated original archive checksums, bounded encrypted metadata and source/destination/group identity. Payload is capped at20MiB before envelope creation and50MiB final archive; it refuses rather than claiming a partial backup. Retained plaintext database files are not created.

Each logical daily/monthly slot gets an immutable encrypted assignment to its original capture group **before capture**. The same-day daily/monthly pair shares one artifact. If an uncertain monthly upload is retried on a later day, its assignment recovers the original encrypted artifact/path, while the new day's daily capture is separate. No new daily historical slot is created to pretend today's data is an older backup. The metadata records the actual injected trusted capture-start clock; due dates are separate. A stale scheduler clock refuses. A changed policy cannot overwrite/reinterpret an unfinished prepared artifact.

`independent-backup-run.ts` is only a sandbox orchestrator. Missing/unapproved policy causes no source or destination activity. It checks destination identity, uses existing prepared bytes before invoking the supplied capture callback, and calls the original private retain/download/checksum/access verifier. Only a matching destination proof can create an immutable encrypted period-completion receipt. On lost upload reply it keeps the exact bytes/path and does not recapture on retry. No automatic retry loop, polling or backfill is added. A prior completion avoids another download, but explicitly reports **previous completion recorded**, not current artifact/inventory re-verification. Partial receipt writing recovers through the same artifact and per-slot records.

## Evidence and limits

Eleven filesystem/orchestrator tests pass: authenticated recovery in a fresh instance; one concurrent winner; disabled/unsafe/shared-key configurations; links/modes/corruption; shared daily/monthly capture; unknown upload response; unapproved policy and wrong destination; exact proof and idempotent completion; capture budgets/paths; retry across Dubai dates; stale clock/policy change. Linked cadence/private destination tests, TypeScript and provider-free build also pass. All destinations/transports and source bytes are synthetic. Source callbacks are not a verified original PostgreSQL exported snapshot and no real Auth or Storage service is contacted.

File/dir fsync and process-level reopen are tested on an owned RAM test directory. This **does not prove persistence after host loss** or provision a durable volume. The real job wrapper must first prove source project identity/read-only snapshot, use the existing bounded capture adapter, and provision approved secure durable storage/credentials. The current driver explicitly reports sourceSnapshotIdentityVerified=false and fullRestoreReadinessVerified=false. It does not create the original signed Owner status proof, which requires actual database restore verification. Database/Auth-login/Storage-service restore verification stays false; decrypting/checksumming an archive is not a database restore test.

Approved independent destination and retention values are still required from the Owner; synthetic values are not adopted. Durable resource provisioning, original capture wiring, actual scheduler, failure alerts, compatible isolated hosted Auth/Storage recovery and final protected approval remain engineering/infrastructure work. No operating data, connection, permission, PR115, real backup inventory or deployment changed.

## Capture claim across processes

The sandbox driver now obtains a create-only0600 authenticated encrypted group claim before a first source capture, then checks again for an already published prepared artifact. A competing process refuses before reading source bytes. The successful or failed live holder removes only its own verified transient claim after completion; no retained archive/receipt is deleted. Different capture groups remain independent. The claim has no timed expiry or automatic stale takeover. A process crash before release leaves the claim visible and blocks new capture until a separately reviewed recovery; already prepared archives remain recoverable without a new source read.

Fourteen spool/orchestrator cases and23 linked cases pass, including a real separate local process holding the claim, deliberate loss of that owned child, unchanged retained claim after refused retry, callback failure/retry, and two sandbox runners producing one capture/upload. No source/provider call occurs in the losing runner. TypeScript/build and189 root cases pass. This addresses concurrent source reads only; RAM host-loss durability, approved independent destination/retention, actual source snapshot capture, hosted Auth/Storage restoration, scheduler and failure alerts remain incomplete. No live backup schedule or original database operation was performed.

The sandbox rechecks which slots are due immediately before a new source capture, after destination verification. If verification crosses Dubai midnight, the expired daily slot cannot acquire a late snapshot or a completion receipt. The next invocation can capture for the new day's daily slot and the current monthly slot. Recovery from an already retained artifact continues to use the original bytes and capture time. This guard does not install a scheduler or change retention.

The isolated encrypted restore drill now checks the restored policies with the runtime role, once as the Owner and once as an employee scoped to another company. It compares the results against the source and verifies retained object bytes and original version checksums. The drill uses an isolated database and a synthetic destination transport.
