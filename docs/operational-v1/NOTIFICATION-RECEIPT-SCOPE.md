# Notification read receipt bound — uninstalled review candidate

The original notification receipt has a tenant/notification/user reference but no direct company. The review candidate follows the actual parent `finance_notifications` RLS/company boundary and checks that the receipt user is the notification's real recipient. INSERT additionally requires that real recipient to equal the actual transaction actor. A system Owner may inspect original read states through an authorized source, but cannot mark another person's notice read on their behalf.

The candidate introduces no new role/grant or privileged lookup, changes no notice recipient, and preserves the original active-account and immutable-history guards. The original API still selects a notice for the current user only before acknowledging. Read receipts remain distinct from replies, completed tasks, customer message delivery and money received. SELECT is a company-bound metadata boundary; it is not a new global notification permission or a replacement for thread/source API authorization.

`backend/review/company-scope-notification-receipts.sql` is excluded from automatic manifests. Its installer requires the reviewed parent, a non-owner/non-bypass runtime and the expected installation actor. Source readiness remains false. Nothing was installed on Supabase or Render.

`backend/tests/company-scope-notification-receipts.test.ts` uses explicitly synthetic technical notices in an owned random localhost DB. It tests selected/empty/unknown/foreign-tenant visibility, forged user IDs, a hidden parent, Owner acknowledgement refusal, allowed own inserts only within rollback, original API own-ack and repeat safety, and exact notice/grant/journal parity. The latest acceptance layers the personnel, customer identity, file/document children, statement children and communication children candidates in the same fake database before executing these checks. This is combined-boundary evidence, not proof that all company/scope permissions or hosted ownership are ready.
