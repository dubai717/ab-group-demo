# Minimal cross-branch collection source — read candidate only

The existing action catalog now contains a separately named `ledger_cross_branch_collect` permission (Arabic/English), independent of ordinary collection, profile or ledger visibility. No existing role, grant or membership is assigned it. Its permission-row addition exists only in the uninstalled review SQL. It grants no additional behavior to original receipt APIs. No duplicate receivables ledger or collection screen is created.

`cross-branch-collection-source.sql` is an **uninstalled** private purpose-source proposal. It reads one specified customer/company relationship proven by original invoices, not all tenant customers. An actual Active non-investor work actor needs a non-revoked explicit company grant issued by an Active original Owner; no group grant, inherited role or delegated authority is inferred in this first candidate. Owner access uses the original Owner identity. An encrypted individual-denial source makes the candidate return review, rather than silently bypassing its undecoded restrictions. The original application separately enforces the actual permission/denial. This conservative limitation is engineering still to complete, not a new Owner decision.

The function is STABLE SECURITY DEFINER with a fixed search path, original tenant and actual actor, private runtime-only EXECUTE and no data writes. Runtime cannot be superuser, bypass RLS or belong to a bypass role. Its exact reviewed body/owner/ACL/kind/volatility/path/runtime are checked by the shared `reviewed-private-json-source.ts`; the original eligibility source uses the same check with its unchanged exact pin. Missing/altered/public/security-invoker sources fail closed. No original protection fingerprint is weakened or repinned.

The TypeScript reader requires READ ONLY REPEATABLE READ with matching actual session/tenant, rejects View As/system/service/investor callers and does not construct an Owner model. Original invoice allocations and shared approved-adjustment arithmetic supply outstanding amounts. Customer ciphertext stays inside the trusted source adapter; the returned identity contains only file number/name/ID, the legal company and collectible original invoice facts. No phone, identity number, passport, salary, bank data, original payload, full profile or ledger access is returned. Unclassified/non-AED/written-off open sources are explicitly counted for review instead of silently claimed fully collectible. `canCollect=false` throughout.

Budgets refuse before large aggregation: one customer ciphertext≤64KiB,100 invoices,640-byte item names,1000 adjustment records and a256KiB packet. Extra adjustment metadata is reduced to the existing bounded document type. Budget refusal returns no invoice rows. There is no polling/global cache; each new read uses current confirmed original allocations. The reader is not registered by server.ts.

## Tested

Two linked native cases (new cross-branch source + original actual-actor eligibility) passed; a final focused source case and provider-free build also pass. The synthetic worker has explicit normal data scope only for company B and a separate purpose grant for company A. It can read A's customer debt minimally while original full customer/ledger/receipt endpoints stay forbidden. Ordinary RLS/profile rights are unchanged. Original confirmed partial collection changes the next source result100→80 without granting read access to the full ledger. Unrelated customer/company, wrong tenant, View As, technical actor, no grant, revoked grant, duplicate/mismatched packet, public EXECUTE, security-invoker drift, an encrypted narrowing source and the101-invoice budget are exercised. Reads leave original customers/invoices/receipts/journals/custody/grants unchanged. Root regressions and TypeScript pass on the documented checkpoint.
