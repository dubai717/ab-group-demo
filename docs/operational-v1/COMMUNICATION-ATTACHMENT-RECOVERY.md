# Original communication file recovery

General-message attachments now reuse the same exact authorized encrypted-file recovery as personnel uploads. The shared implementation is `retained-encrypted-upload.ts`; the original personnel exports retain their names, identity calculation, errors and behavior. There is no new file store, upload endpoint, overwrite, deletion or background read. Existing communication keys, scanner, immutable message metadata, source recipients and audit stay in place.

A normal successful upload performs no recovery read. A create-only conflict or uncertain upload reply reads only the exact retained key and verifies decrypted canonical base64, size and SHA256. It refuses a different/corrupted object. Definite authorization/quota/provider errors do not become success. A rolled-back message transaction may leave the already encrypted file; retrying the same original client key verifies it and creates the original message once. It does not invent a new file path or delete the retained object. Newly entered attachment base64 must be canonical. Downloads verify the original stored size as well as digest before returning bytes/auditing a successful read.

The linked12-case personnel recovery/master-package set passed after extraction; a new native original general-message case passes lost reply, rolled-back late audit, exact-key recovery, no duplicate messages/files, participant-only download, corruption refusal without success audit, noncanonical upload refusal and unchanged original invoices/receipts/journals/custody. TypeScript passes. These are synthetic local fixtures, not hosted Storage or real WhatsApp attachment acceptance. The official media reader remains unregistered and still requires original source/attachment integration.
