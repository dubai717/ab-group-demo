# Dated reminder preview settings — unpublished

The existing expiry dialog opens an Owner-only setting form for company, current document type, or current customer/type when an actual customer source exists. It reuses original encrypted settings, audit, session/CSRF, request receipts, company/customer/vehicle identities and the existing forms; no new role, duplicate directory or migration.

Changes record an explicit effective date (today/future), reason, chosen offsets and preview-enabled state. Every successful change appends a dated record and a complete encrypted version through the API. The current pointer retains history and future rules. Selection uses exact customer/type, customer, type, company, then default30/0; only effective records participate. Within a scope, later effective date and revision win. This technical precedence is explicit; no fee or tax rule is inferred. A customer-specific rule requires an actual primary-company or vehicle-company relationship and cannot create one.

The source carries actual Owner/time/revision and canonical UUIDs. Changed rule identity/content conflicts, stale revisions and duplicate offsets are rejected. Same receipt or same rule ID/body cannot duplicate a version. Invalid fields remain correctable. Unknown save outcomes freeze the exact body; acknowledged readback failures retry GET only. The original visible expiry cards refresh after verified save. Dates do not mutate document metadata or previous financial records. Company settings are fetched once in a bounded batch on the original expiry read, without polling or object-byte downloads.

`enabled` controls preview scheduling only. `liveEnabled=false`, `externalSent=false`, serviceFee0AED and no financial effect remain explicit. A paused higher-specificity rule suppresses its matching preview. Stable event identity binds the current document/version/expiry/offset; changing a setting does not invent a second identity for the same reminder. No dispatch queue, delivery proof, message scheduler, real provider connection or operational activation is claimed. A future scheduler must re-read current source/consent/settings before sending and suppress old queued versions.
