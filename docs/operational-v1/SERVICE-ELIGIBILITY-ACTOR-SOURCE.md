# Actual actor eligibility source — review only

The original Owner simulation and approved last-two-actual-due-month evaluator are reused. An original posted manual `financial` invoice classified as `loan` now requires source review if no verified periodic contract exists; it cannot silently disappear from eligibility. This does not reclassify debt or count a book writeoff as payment.

`backend/review/service-eligibility-source.sql` is an **uninstalled proposal**. It is absent from runtime manifests and server registration. The private stable, fixed-search-path reader uses the actual tenant/actor, Active/work-access guard and original scoped customer identity. A worker without an explicit reviewed scope receives only a review header, never the legacy unrestricted financial fallback. Investor, unknown/inactive actor, unrelated customer, other tenant and arbitrary date are denied. There is no Owner impersonation, role change, scope grant, new ledger or financial write.

A bounded snapshot includes only this customer's original periodic/loan invoice facts, original allocation total, adjustments, encrypted verified contract/event metadata, relevant case books and unapplied cleared receipts. All privileged joins carry tenant predicates. Limits are 100 companies, 20,000 source rows per collection, 500 case books and 8 MiB serialized packet; overflow requires review rather than truncating into an allowed result. This private server packet must never be returned by a public HTTP route.

`service-eligibility-actor-source.ts` validates context, limits, completeness and the explicit reviewed function-body pin plus ownership/ACL/stability/search path. It reuses the original receivable amount helpers and evaluator. Its unregistered review adapter additionally checks original actual service-create permissions, current active company, customer rights, original DB actor/tenant and a read-only repeatable-read snapshot; View As is refused. The output contains only decision/amount/reference/source-version facts, not company/vehicle/invoice identifiers, names or decrypted source payloads.

## Reproducible isolated acceptance

`service-eligibility-actor-source.test.ts` installs proposals only into its own random synthetic `ab_backup_*` database on loopback. It compares the actual worker result with the original Owner review for two companies, unequal fees and original contracts, while ordinary worker invoice queries remain company-restricted and the normal ledger API remains forbidden. Vehicle/residence/general source reviews use the original permission model. Missing explicit scope, other customer/tenant, context mismatch, duplicate/incomplete/oversized packet, View As, impersonated session, out-of-scope company, public EXECUTE and invoker drift are refused. Journal/receipt/invoice/task/grant counts and DB identity remain unchanged by review.

## Not complete or active

No service controller guard, timed exception, prospective activation marker, creator/approver/executor integration, cross-branch financial action or live scope application is claimed here. Full compiled source/dependency/privileged-function readiness and acceptance remain dependencies. No automatic scope activation or legacy policy repinning. Existing services, receipts, collection, deposits, complaints and document updates are untouched. Final integration must enforce this policy on original new-service actions, preserve old started-service evidence, remain transactionally safe, and return a localized minimal response without exposing the private snapshot.

## Bounded source before JSON aggregation
The proposal checks company count before financial collection. Individual encrypted invoice/contract/confirmation metadata over64 KiB or case books over256 KiB return a review-only header, as does combined relevant payload over6 MiB before JSON aggregation. The serialized8 MiB guard remains. This avoids assembling an unbounded large ciphertext packet merely to reject it afterwards. A new append-only synthetic contract-confirmation event proves the refusal returns under1 KiB with no invoice array. No immutable financial record or trigger was changed. The first attempted test update was rejected by the existing immutable-invoice guard and was replaced by append-only fixture setup; that failed test is not recorded as acceptance. Only the new uninstalled function body pin was explicitly revised; existing scope pins were not changed.
