# AB Group — نتيجة فحص الإزالة وخطة قاعدة اختبار نظيفة

## القرار الفني والحالة

لم يُحذف أي صف أو ملف، ولم تُنفّذ تسويات أو إلغاء أو عزل أو إخفاء للمجموعة. لم تتغير RLS أو Triggers أو الصلاحيات أو المخطط أو الأسرار أو Render أو قاعدة الاتصال. لم يُنشأ مشروع سحابي جديد. لا يمكن إتمام الإزالة الفعلية لمجموعة TEST_DATA ضمن شروط إبقاء حماياتها الحالية فعّالة؛ بناءً على البند 6، البديل المقترح هو قاعدة اختبار جديدة من المخطط المعتمد، مع إبقاء الأصل والنسخ الاحتياطية والبيانات الأخرى دون تغيير.

النطاق المحدد سابقاً لا يزال مبنياً على فهرس `TEST_DATA:integrated:v1` والمعرفات وبصمة المعاينة `ad6975a70f3553ba915f5fca42c6c7e95da0f2f467b5e7c4603b80dadd0b79c9`، وليس الأسماء. لم تُوسّع القائمة إلى بيانات جديدة أو سجلات خارجها. لا يوجد منفّذ حذف أو تجاوز في هذا الفرع.

## الأدلة الحالية

- استُرجعت النسخة المشفرة الموجودة من المخزن الخاص، وفُك تشفيرها وتحققت بصمتها وبصمات محتوياتها دون عرض الأسرار. أُعيدت استعادتها فعلياً في PostgreSQL مؤقت على GitHub runner فقط، وطابقت الجداول والصفوف والقيود والمشغلات وRLS. تحققت 96 وثيقة مشفرة، وفشل وصول ab_runtime في النسخة المعزولة إلى شركات دون سياق Tenant كما ينبغي. النسخة الأصلية لم تُستبدل أو تُحذف.
- مسار النسخة داخل `ab-private-test`: `ab-group-backups/v1/20261105T100805359Z-904cef09-e839-4e8f-996d-63adc31226f6/database.abbackup`.
- طابقت تعريفات Triggers التسعة عشر في القاعدة الحالية تعريفاتها المحفوظة في المعاينة. 18 حماية غير مشروطة، والحماية الأخيرة تخص القيود المرحّلة. كل القيود الـ358 المعنية حالتها Posted واتزانها قائم؛ لم تُنشأ قيود عكسية أو تُصفّر أرصدة جزئياً.
- لا توجد دالة purge/cleanup مخصصة في مخطط ab الحالي. مسارات العكس والتسوية وإعادة الجدولة تنشئ سجلات جديدة وتحتفظ بالأصول، ولذلك لا تحقق شرط الإزالة الفعلية ولا تصلح بديلاً جزئياً هنا.
- هويات المالك الأصلي والمستخدمين التجريبيين العشرة وأدوارهم مطابقة للمرجع، وتوجد محققات كلمات مرور للحسابات الإحدى عشرة في Auth. لا يعني ذلك أن نسخ جدول ab.users وحده ينقل المصادقة؛ يجب استخدام طريقة Auth مدعومة واختبارها قبل أي تحويل، دون إعادة تعيين كلمة المالك أو تغيير auth_id تلقائياً.
- سجل الترحيلات الحالي يطابق النسخة المحفوظة والمخطط 001–013. فحص المصدر كان داخل معاملة READ ONLY مع session_replication_role=origin؛ لم يُغيّر وضع حماية المصدر.

## البديل المقترح للموافقة المستقلة

1. إنشاء مشروع Supabase Free تجريبي منفصل إذا كانت حصة الحساب المجانية تسمح، بلا ترقية مدفوعة أو خدمات جديدة أخرى. لا تنفيذ قبل الموافقة. استخدام خدمة Render الحالية مستقبلاً؛ لا حاجة لخدمة Render إضافية.
2. تطبيق ملفات المخطط المعتمدة 001–013 في المشروع الجديد فقط، مع الصلاحيات وRLS والمشغلات المعتمدة وسجل الترحيلات. لا إعادة تأسيس أو تعديل للمشروع الحالي.
3. اعتماد قائمة نقل صريحة: منظمات/ملفات الهوية اللازمة للمالك والـ10 مستخدمين، وأدوارهم ومصفوفة الصلاحيات والتفويض، والمراجع الأساسية والإعدادات المعتمدة ودليل الحسابات المرجعي بلا أرصدة أو حركات. لا شركات أو عملاء أو مركبات أو فواتير أو تمويلات أو سندات أو مهام أو تنبيهات أو وثائق من مجموعة TEST_DATA القديمة، ولا استيراد عام لبقية بيانات المصدر. تبقى أي بيانات أخرى، بما فيها بيانات حقيقية أو تجارب أحدث، في القاعدة الأصلية ولا تُحذف؛ نقلها يحتاج قائمة مستقلة إذا طُلب لاحقاً.
4. نقل هويات Supabase Auth بالطريقة المدعومة بعد فحص توافقها، مع حفظ المعرفات والتحقق من محققات كلمات المرور وتأكيد الحسابات. لا كلمات مرور مكشوفة، ولا إعادة تعيين أو إنشاء مالك بديل، ولا نسخ جلسات قديمة أو refresh tokens. إذا لم يمكن ضمان هذا النقل نتوقف قبل التحويل ولا ندّعي حفظ تسجيل الدخول.
5. حفظ الأسرار الجديدة في بيئة محمية منفصلة مثل supabase-test-clean دون استبدال أسرار البيئة القديمة أو مفاتيح فك النسخ. إنشاء Bucket خاص في المشروع الجديد بعد الموافقة، بلا نقل وثائق TEST_DATA القديمة. تُراجع أي مرفقات ضرورية لحسابات المستخدمين بقائمة منفصلة، لا بنقل شامل.
6. إعادة اعتماد ربط الشركات والبنوك والصلاحيات على الكيانات الجديدة، دون توسيع صلاحيات المستخدمين أو إسقاط نطاقاتها بصمت. فحص حي: 14 تعريفاً للدليل في نطاق الحسابات المعنية، منها 14 تعريفاً ورد في فهرس TEST_DATA، و42 ربطاً بشركات و7 ربطاً بنكياً، و10 عضويات شركات، و0 تفويضات إضافية. نسخ هذه الروابط كما هي إلى قاعدة بلا كياناتها يخالف العلاقات؛ يلزم اعتماد خريطة ربط أو قائمة مرجعية ضرورية قبل إعلان الصلاحيات والدليل مكتملين. تُحفظ نسخة الدليل الأصلي ولا تُحذف تعريفاته أو تُعدّل أسماؤه تلقائياً. يمكن تجهيز التعريفات كقوالب بلا أرصدة، ثم ربطها بالشركات والبنوك التي تُنشأ يدوياً وفق خريطة معتمدة.
7. تجهيز نسخة برنامج تستهدف المشروع الجديد صراحة وتحدّث البصمات المسموح بها وحراسة Test Users للمشروع التجريبي الجديد فقط، وتُبقي حسابات Test Users. إخفاء شاشة Test Data القديمة بعد اكتمال الانتقال، دون إخفاء سجلات داخل المصدر أو حذف شاشات التشغيل.
8. اختبار المصادقة والمالك والأدوار وRLS ودليل الحسابات وحفظ الشركات والعملاء والمركبات واسترجاعها من الواجهات الأصلية على نسخة قبول معزولة. يجب تعديل آلية live smoke التي تُنشئ سجلات وهمية دائمة حتى لا تعيد ملء الهدف النظيف؛ لا تُزرع حزمة TEST_DATA جديدة. إدخال سجلات التجربة اللاحقة يكون من الشاشات وبموافقة المستخدم، وتُحفظ حتى نهاية التجربة الشاملة.
9. تقرير قبول وخطة رجوع برمجية واتصالية قبل أي Cutover. لا تغيير DATABASE_URL أو Supabase URL/keys أو اتصال Render أو النشر الذي يبدّل الهدف إلا بموافقة مستقلة على البصمة والربط النهائيين. يبقى المصدر والنسخ القديمة متاحين للرجوع؛ لا حذف للمشروع القديم ولا بياناته خارج المجموعة.

التكلفة المستهدفة للمشروع الجديد صفر ضمن Supabase Free المتاح، وخدمة Render الحالية وخطتها تبقيان كما هما. لم تُفحص حصة مشاريع الحساب أو تُشترَ خدمة؛ إذا لم تتوافر حصة مجانية لا توجد ترقية تلقائية.

## المتبقي وما يحتاج موافقة

المتبقي هو إنشاء المورد الجديد، اعتماد قائمة النقل وخريطة النطاقات والدليل، والتحقق الحقيقي من المصادقة والواجهات على الهدف الجديد، ثم موافقة مستقلة لتبديل اتصال Render والنشر. لم تُنفّذ اختبارات إنشاء سجلات جديدة على القاعدة الحالية حتى لا نضيف بيانات وهمية أخرى أو ننفّذ حلاً جزئياً. النتيجة الحالية: صفر حذف، وصفر إلغاء/تسوية/عزل، والمصدر والحسابات والصلاحيات محفوظة. الحسم المطلوب الآن هو الموافقة على مسار المشروع التجريبي الجديد؛ لا تعني هذه الموافقة تحويل Render أو لمس بيانات المصدر.
