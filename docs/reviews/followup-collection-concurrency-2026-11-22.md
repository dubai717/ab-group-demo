# قبول تزامن رسوم المتابعة والتحصيل — دون تغيير قواعد الرسوم

الفحص وجد أن `core.transaction()` يستخدم قفل المؤسسة الأصلي قبل تنفيذ واجهات الحفظ، وأن `financialTick()` يستخدم الدالة نفسها للعامل المجدول. لذلك لم تُضف أقفال أو نظام توزيع بديل، ولم تتغير سياسة الستين يوماً أو قيمة الرسوم أو الفترات أو الصلاحيات.

اختبار تكاملي معزول فعلي:

1. ترتيب قاعدة شهرية معتمدة في fixture وهمي فقط، ومركبة مسجلة وفاتورة أصل سالك مستحقة لأكثر من 60 يوماً.
2. إيقاف العامل عند حد إنشاء فاتورة الرسم بعد احتساب الخطة وقبل إدخالها؛ إرسال تحصيل أصلي بالتوازي والتحقق من انتظار PostgreSQL الفعلي على قفل المؤسسة، لا الاكتفاء بمؤقت أو نجاح وعد JavaScript.
3. تحرير العامل؛ رسم واحد 10 AED وقبض الأصل 100 AED. رسم القرار الذي سبقت معاملته السداد يبقى محفوظاً، ولا يُلغى تلقائياً.
4. إعادة العامل مرتين بالتوازي: لا فاتورة مكررة للفترة.
5. مركبة ثانية سُدد أصلها أولاً: لا رسم جديد. الرسوم السابقة وحدها لا تعيد تشغيل الرسوم.
6. قيمة الفاتورة الأصلية والصلاحيات ثابتة. لا بيانات فعلية أو كتابة على Supabase.

الحالة نجحت على المحرك الأصلي **دون أي تعديل لكود التشغيل**. القبول التراكمي لنقطة `eebceda` نجح: **498 اختباراً، صفر إخفاق**؛ الحالة الإضافية السابقة ليست داخلة في ذلك العدد. تختبر GitHub الإضافات في فرع البناء فقط؛ لا طلب نشر.

الملفات: `backend/src/core.ts`، `backend/src/financial-jobs.ts`، `backend/src/financial-package.ts` و`backend/tests/followup-collection-concurrency.test.ts`.
