## المنفذ فعلياً

- توسيع `finance_entries` ليبقى دفتر قيود واحداً: مصدر بنكي قائم أو قيد محاسبي جديد، وليس سجلين لنفس المال. قيود يدوية تحتاج اعتماداً، وقيود تلقائية للفواتير والقبض والصرف والنثريات والبطاقات والتسويات؛ توازن إلزامي، أرقام مستقلة، منع تكرار المصدر، عكس موثق وعدم تعديل المرحل.
- دليل حسابات موحد، مرتبط بحسابات كل شركة وعملتها؛ حسابات رئيسية وفرعية، تعطيل/تفعيل وتعديل الأسماء وحماية طبيعة الحساب المستخدم. تعريف بنود مالية قابل للإدارة، مع ربط الحسابات وأولوية التحصيل ونطاق الشركات ووسائل الإنشاء والسماح بالفاتورة/القبض/الصرف.
- استخدام جدول الفواتير القائم وإتاحة فواتير مستقلة دون مركبة، وتصحيح موثق دون حذف، وتفصيل المستحق والمسدد والرصيد. تصنيف الفواتير السابقة غير المسددة وغير المعدلة بالدفتر يتطلب مراجعة صريحة؛ لا يُخترع تاريخ محاسبي للفواتير التاريخية المسددة.
- استيراد CSV/XLSX مع ربط الأعمدة، تأكيد العميل والمركبة واللوحة والشركة والبند، معاينة، عزل غير المطابق والمكرر، اعتماد ذري، حفظ المصدر مشفراً وإتاحته للمخول، ومنع إعادة الاعتماد. ملفات الاختبار وهمية.
- تحصيل متعدد البنود بوسيلة واحدة، سند مستقل لكل بند، تحصيل جزئي وتوزيع آلي بالأولوية والأقدم استحقاقاً؛ تجاوز الأولوية بتفويض مستقل وسبب. الزائد أمانة/رصيد دائن وليس إيراداً. التحويل البنكي المعتمد لا يدخل عهدة نقدية ولا يُرحّل مرة أخرى.
- توسيع سندات القبض الحالية وسجل الشيكات والعهد: شيك واحد لعدة سندات، عدم تسديد الفاتورة قبل التحصيل، عكس التخصيص والقيد عند الارتجاع دون إنشاء مديونية مكررة. المسار القديم ممنوع من إعادة معالجة سندات/شيكات المرحلة الخامسة أو تخصيص التحويل نفسه مرة ثانية.
- حركات عهدة جزئية مؤرخة، فصل الشركة والعملة والنقد/الشيك، مسارات تسليم مؤرخة وبديل مؤقت، تأكيد من المستلم المحدد فقط؛ ينتقل المستلم الفعلي ويبقى الفرق على العهدة الأصلية. لا استقطاع راتب أو إدانة تلقائية. تسليم الشيكات الكاملة منفصل عن التجزئة النقدية.
- إيداعات جزئية/كاملة بمستند خاص، لا إغلاق قبل تحقق مخول من الحساب والتاريخ والمبلغ. المستند المحجور يمنع التأكيد، والمبلغ غير المؤكد يبقى في العهدة. إيصال الإيداع ليس مطابقة بنكية نهائية، وOCR غير مفعل.
- سندات صرف معلقة، تجهيز الشيك مرة واحدة، معاينة اعتماد فردية/جماعية بمستفيدين وإجماليات منفصلة، رمز تأكيد مرتبط بالمستخدم والمراجعات ومهلة 10 دقائق؛ تأكيد نهائي، عدم اعتماد مرتين، فصل الاعتماد عن صرف البنك، وإلغاء موثق/قيد عكسي دون حذف الأصل.
- Work Amount: فاتورة التزام تجاه العميل وليست إيراد المكتب، مجموع قبوض يساوي الشيك، قبوض منفصلة للمستحقات والصافي والعمولة عند وجودها، وسند صرف صافي واحد بحالة Pending. يدعم API العمولة المستقلة، والواجهة الأساسية تعرض المسار دون عمولة اختيارية.
- صناديق شركات ونثريات متعددة مع مسؤول وسقف وحد تنبيه وافتتاحي صريح ومقابل حقوق ملكية؛ صرف ضمن التفويض وتغذية تحويلية لإعادة السقف دون مصروف مكرر.
- بطاقات بآخر أربعة أرقام فقط؛ توزيع مبلغ العملية على شركات/عملاء ومركبات، قيود متقابلة عند استخدام شركة أخرى، تنبيه فاتورة ناقصة لا يزول بمجرد متابعة، وسجل من أكمل الفاتورة ووقت الإنجاز.
- كشوف بطاقة وبنك مرتبطة بالأرشيف الخاص، إدخال/مراجعة يدوية عند غياب OCR، مطابقة الحركات الفعلية وعدم اعتماد الفروقات، وسند صرف بطاقة مجمع لكل شركة وشهر لا يتكرر. التحويل بين الشركات يمر بسند/شيك ومقابل حسابات جارية، ولا يُنشئ إيراداً أو مصروفاً تشغيلياً بمجرد التحويل.
- فحص إغلاق شهري للقيود والصناديق والعهد والإيداع والصرف والشيكات والمطابقات والبطاقات والتحويلات والفواتير غير المصنفة؛ منع الإغلاق عند النقص، ومنع الترحيل للفترة المغلقة. يمكن قيد قبض حالي لفاتورة قديمة في فترة مفتوحة. إغلاق المجموعة يتطلب إغلاق الشركات.
- ميزان مراجعة وأستاذ ويومية وربح وخسارة وميزانية مشتقة من قيود فعلية، وأرصدة/أعمار مستحقات وتقارير عهد وصرف وبطاقات ووقائع أداء دون أوزان تقييم. مبالغ الشركات والعملات منفصلة. التصدير CSV آمن من صيغ الجداول، وExcel XML والطباعة/PDF من المتصفح؛ الصفحات 200 صف.
- تقرير VAT إداري من حسابات ضريبة مُعرفة وقيود فعلية، مع فصل صافي/ضريبة الفاتورة وتصحيحها بدقة. ليس إقراراً ضريبياً معتمداً. يدعم API استبعاد الأرصدة المتبادلة المعرفة عند اختيار جميع الشركات وتوازنها؛ يمنع الإيهام بإلغاء أرصدة غير متوازنة.
- شاشة مالية بالقائمة العمودية وتبويبات أوامر أفقية، وزر تحصيل من ملف المركبة. النماذج تحفظ المدخلات في الذاكرة عند الخطأ فقط؛ لا كلمات مرور أو رموز جلسات أو وثائق أو معاملات في localStorage. سجل قبل/بعد مشفر غير قابل للتعديل للعمليات المالية.

## وظائف جزئية أو غير مفعلة — لا تعتبر مكتملة

1. الفوترة التلقائية السابقة للعقود وخدمات المركبات محفوظة. ربط الفواتير القديمة بالتصنيف المحاسبي تتم مراجعته؛ عامل بنود عامة دوري شهري/سنوي منفذ، يتجنب تكرار فواتير العقود والخدمات الأصلية ويصدر السنة التالية خلال ديسمبر. يحتاج تفعيل الشركة وFINANCIAL_JOBS_ENABLED معاً، وكلاهما متوقف افتراضياً. ربط جميع التسويات التاريخية للمرحلة الرابعة تلقائياً بالدفتر ليس مكتملاً. لا تُرحّل فواتير تاريخية مسددة تلقائياً. التقارير تعرض عدد الفواتير وتعديلات الفواتير غير المصنفة، والإغلاق يحظر إخفاء النقص.
2. فحص مواعيد الإيداع وتقويم أيام العمل والعطلات ومراحل البطاقة ويوم 5 موجود، مع منع تكرار الإشعارات اليومية. تشغيله من زر مخول أو العامل الخلفي الاختياري المنفذ والمختبر؛ لم يُفعّل على Render. يُعاد التحقق من تفويض صاحب الإعداد عند كل تشغيل، مع سجل يميز هوية الخدمة. لا تدّعي الواجهة إرسال SMS/WhatsApp أو تشغيل عامل دوري.
3. قراءة PDF/OCR وخلاصة مصرفية مباشرة غير متاحة. يمكن رفع الأصل ومراجعته وإدخال صفوف الكشف يدوياً؛ تحويل كشوف البنك/البطاقة من Excel تلقائياً ليس مكتملاً. استيراد الفواتير Excel يعمل بشكل مستقل.
4. مطابقة البطاقة تدعم المشتريات المسجلة وسداد السندات المصروف بنكياً، وتجميع عدة سندات بسطر سداد واحد مع تطابق المجموع والتاريخ. تسجل الرسوم/الفوائد غير المسجلة كعمليات فعلية بعد المراجعة؛ تبقى الفروقات غير المفسرة معلقة ولا تُغلق قسراً. يلزم اختبار كشف حقيقي مجهّل لاحقاً، دون ادعاء تشغيل تكامل خارجي.
5. التدفق النقدي الحالي عرض لحركات الحسابات المصنفة/البنكية، وليس قائمة تدفقات نقدية مكتملة ومُعتمدة وفق معيار محاسبي. واجهات بعض التقارير المتقدمة والفلاتر/ترتيب الأعمدة تحتاج استكمالاً. تطبيق الرصيد الدائن لفواتير لاحقة والجرد الفعلي وتسويته بعد التحقق منفذة، دون قبض/مصروف مكرر أو خصم راتب. إذا ارتجع شيك مصدر الرصيد يُعكس التطبيق وتعود المديونية، مع إبقاء التاريخ. ميزان المراجعة والربح والخسارة والميزانية الأساسية من قيود فعلية.
6. تعريف VAT يحتاج اعتماد الإعدادات القانونية والمراجعة الضريبية قبل الاستخدام الحقيقي؛ لا توجد إقرارات جاهزة للتقديم. الإلغاءات/الشطب والعكس من المسارات السابقة تحتاج تصنيفاً ومراجعة محاسبية شاملة قبل الاعتماد الإنتاجي؛ تظهر تعديلات الفواتير غير المرحلة ضمن نواقص التقرير/الإغلاق. تحصيل دين مشطوب محاسبياً يتوقف للمراجعة بدلاً من ترحيل استرداده كقبض مستحقات عادي خطأً.
7. مستندات التأكيد القانونية/البنكية تبقى محجورة دون ماسح ملفات حقيقي. لا فحص وهمي في الإنتاج. موفرو Auth والتخزين/الفحص في الاختبارات محاكاة معلنة، ولا تثبت نتائجهم مصادقة سحابية بكلمة مرور أو فحص مستند حقيقي.

## قاعدة البيانات والتوافق

`supabase/proposed/012_financial_management.sql` مقترح فقط، بعد 009→010→011. ينشئ جداول الحسابات الموحدة والبنود والقيود والفترات وتصنيف الفواتير ودفعات القبض وعكس التخصيص وحركات/مسارات وتسليم العهد والإيداعات والصناديق وسندات الصرف ودفعات الاعتماد وWork Amount والبطاقات وتوزيعها ومطابقتها وتسويتها والتحويلات والاستيراد ووقائع الأداء وتطبيق الأرصدة الدائنة وإغلاق المجموعة، مع توسعة سجل المهام القائم دون إنشاء خدمة جديدة.

يوسع الجداول السابقة دون حذف سجلات: `finance_chart`, `finance_entries`, `finance_receipts`, `finance_statements`, `vehicle_invoices`, `vehicle_allocations`. توسيع القيود يسمح بفاتورة دون مركبة وبشيك لعدة سندات؛ يظل المسار القديم مدعوماً ومحميًا من التكرار مع المسار الجديد. جميع الجداول الجديدة tenant-RLS وعلاقات مركبة، دون صلاحيات DELETE. السجلات التاريخية غير قابلة للتعديل، والمبالغ `numeric(21,3)` وحسابات BigInt. الترحيل يضيف/يستبدل قيود تحقق ودوال حماية؛ يحتاج مراجعة وأقفالاً قصيرة وقد يتوقف عند تعارض بيانات قائم. لا توسعة تلقائية لتعيينات صلاحيات المستخدمين.

ملفات وبصمات 009–012 مثبتة في `backend/deploy/financial-release-plan.json`. أداة `financial-release.ts` تتحقق من موافقة محددة وفرع تفعيل منفصل وبصمات وسجل الترحيلات والجداول وRLS والعلاقات؛ تتوقف عند جداول موجودة غير مسجلة أو نسخة احتياطية بلا إثبات استعادة حديث، وتطبق المفقود في معاملة واحدة فقط. `financial-release.yml.example` قالب خامد، ليس Workflow نشر فعالاً. إثبات الاختبار الوهمي ليس إذناً أو إثباتاً لاستعادة نسخة Supabase الفعلية.

الجدولة الجديدة لا تحتاج اشتراكاً: نفس عملية Node.js، متوقفة افتراضياً، مع تفويض شركة منفصل وفحص مستخدم الإعداد عند التشغيل. لا تغيّر هذه الإضافة متغيرات Render الحالية.

## الاختبارات والتسليم

اختبارات API محلية فعلية تغطي الفاتورة والقبض والأمانات والأولوية والشيكات والعكس والعهد الجزئية والإيداع الجزئي والاعتماد المزدوج والإلغاء وWork Amount والنثريات والبطاقات والتسويات المتقابلة ومطابقة البنك والضريبة والاستيراد والإغلاق الإيجابي/المرفوض ومنع الترحيل المغلق والصلاحيات وعدم تكرار الأموال. توجد تجربة استعادة قاعدة ومستندات مشفرة إلى هدف محلي جديد، وفحص حماية المصدر/العلاقات/RLS وعدم تغيير الأدوار. تُحفظ قواعد الاختبار القديمة ولا تُحذف.

اختبار المتصفح ينفذ إنشاء فاتورة وتحصيل جزء منها وإعادة الفتح بالرصيد الدقيق، وتبويبات الوظائف والعربية/الإنجليزية و1440/1024/768/390 والوضعين دون أخطاء JavaScript أو تخزين حساس بالمتصفح. توجد حالة مستقلة عند غياب 012 تمنع الحفظ الكاذب وتحافظ على الدخول والواجهة السابقة.

GitHub CI يعيد اختبارات المراحل السابقة والخلفية والجديدة ومتصفحات الشركات والبنوك والعملاء والمركبات والمالية بحالتي المخطط، ويبني Docker دون أسرار أو نشر. نتائج التشغيل النهائية وروابطه في Pull Request؛ نجاح الاختبارات لا يعني نشر التعديل.

## Render والنسخ والاستعادة

تظل الخدمة الحالية https://ab-group-demo.onrender.com والفرع المخزن بالإعدادات `staging/ab-group-test` والنشر اليدوي. لم تُغيّر `render.yaml` أو الأسرار أو CA أو إعدادات Supabase/Render. آخر فحص سحابي للقراءة فقط في المرحلة الرابعة تحقق من TLS وab_runtime وAuth والتخزين الخاص وثمانية ترحيلات وبصمة الواجهة؛ لم يُكرر لمجرد هذه المرحلة. لا توجد صلاحية فحص إعدادات Render المحمية مباشرة هنا، فيجب تأكيد الفرع/النشر اليدوي قبل التفعيل.

الفحص السابق وجد `BACKUP_ENCRYPTION_KEY` المستقل مفقوداً/غير صالح؛ لم يُغيره هذا العمل. يجب توفيره عبر مدير الأسرار المعتمد، ثم التقاط نسخة سحابية مشفرة والتحقق من استعادتها إلى هدف معزول متوافق مع Auth/Storage قبل أي تغيير. اختبارات الاستعادة المحلية لا تحل محل استعادة النسخة السحابية الحقيقية. لا تُرفع ملفات dump أو المفاتيح أو بيانات التشغيل إلى GitHub.
