## حدود واضحة وأعمال باقية

- **الترحيل 009 مقترح فقط:** موجود خارج مجلد الترحيلات الآلية في `supabase/proposed/009_financial_workbench.sql`. لم يُطبق سحابياً. تعمل الواجهات السابقة على الترحيلات الثمانية وحدها؛ المالية الجديدة تعرض عدم جاهزية المخطط بدلاً من حفظ محلي أو نجاح كاذب.
- لا OCR أو قراءة PDF/Excel آلية أو ربط مصرفي مباشر أو FX. الأصل يُرفع بالأرشيف القائم، والمراجعة يدوية. لا تحصيل آلي من صورة الإيصال، ولا رسائل خارجية أو خدمة مدفوعة.
- ربط العميل/العقد/المركبة/القسط **مراجع تكامل فقط**؛ وحداتها لم تُنشأ أو تُخترع، ولا يتغير أي قسط إلى «مسدد» في وحدة غير موجودة.
- دليل محاسبي صريح خاص بكل شركة، ونواة قيد مزدوج للعمليات البنكية. ليست محاسبة عامة مكتملة: افتتاحيات دفتر الأستاذ، سياسات FX، قوائم الدخل/المركز المالي/التدفقات/ميزان المراجعة والموازنات والاستبعادات المجمعة تحتاج قواعد محاسبية معتمدة وتنفيذاً لاحقاً. الملخص المجمع بنكي فقط ولا يجمع عملات مختلفة.
- لا تحرير لمسودات مالية محفوظة في هذه المرحلة؛ يُرفض الطلب الخاطئ مع السبب ثم تُنشأ مسودة مصححة بمرجع جديد. لا حذف ولا استبدال لقيود معتمدة.
- لا إدارة تلقائية لحذف الملفات، ولا مجدول خارجي لتنبيهات الشيكات. التنبيهات محسوبة عند فتح الوحدة. مؤشرات التخزين لا تشمل الملفات خارج سجل البرنامج.
- قائمة تشغيل الوحدة محدودة بأحدث 500 سجل لكل نوع؛ التقارير قابلة للتنقل على جميع الصفحات. لا توحِ شاشة التشغيل بأنها سجل تاريخي غير محدود.
- تخزين الملفات الحقيقي يبقى خاصاً ومحجوراً حتى تشغيل فاحص الملفات الفعلي. استخدام fake Auth/store/scanner محصور في fixtures الاختبار المحلية؛ لا يعتبر دليلاً على فحص ملف حقيقي.

## الاختبارات

البيانات كلها وهمية وفي قواعد PostgreSQL محلية منفصلة؛ لا تعديل أو حذف لبيانات الاختبار السحابية أو المحلية السابقة.

- بناء TypeScript إلى JavaScript: نجح.
- اختبارات جذر المشروع: نجحت 10 ملفات، بما فيها ترحيل بيانات المتصفح القديم، الحسابات/الشركات/المستخدمون والقواعد المالية وحماية استجابات بيانات الوحدة والتقارير المتأخرة بعد الخروج من الظهور لمستخدم آخر.
- اختبارات Backend: نجحت 58 حالة تشمل RLS والتفويض والمصادقة والوثائق واستعادة النسخة الاحتياطية القديمة و6 سيناريوهات مالية متعددة الخطوات.
- الاختبارات المالية تشمل توازن التحويلات لكل شركة، دقة الكسور، إعادة الطلب، منع تغيير افتتاحية حساب بعد قيود مالية، عدم انتقال العهدة قبل الإقرار، منع إثبات التحصيل من مجرد الإيداع، منع اعتماد كشف غير مطابق، عزل الشركات والمجموعات، منع إدخال قيد غير متوازن/تعديل قيد معتمد، التدقيق المشفر والإشعارات غير المكررة والتقارير المحكومة.
- متصفح Chromium: إنشاء شركة وحساب ومدير حساب بالحفظ المركزي المحلي، مسودة مالية لا تُعتمد عند غياب المقابل المحاسبي، سجلات وتقارير، العربية/الإنجليزية، 1440/1024/768/390 بكسل، وضعي فاتح/داكن، وعدم أخطاء JavaScript أو كتابة مالية حساسة في تخزين المتصفح.
- تستكمل نتائج حالة غياب 009، والواجهة السابقة، وصورة Docker والفحص السحابي للقراءة فقط في سجل التسليم أدناه.

## التشغيل الآمن للمراجع

بعد `npm ci --ignore-scripts` و`npm run backend:test:db`، لتجربة **وهمية محلية فقط**:

```sh
AB_TEST_FINANCE_SCHEMA=yes node --import tsx backend/tests/serve-finance-fixture.ts
```

الخادم على `http://127.0.0.1:3200`؛ بيانات الاختبار المولدة في `work/finance-browser-fixture.json` المتجاهل من Git، وليست حسابات Supabase. `node backend/tests/finance.browser.cjs` يجرب الواجهة آلياً. لإثبات حماية النسخة ذات الثمانية ترحيلات فقط، أوقف خادم الاختبار وشغله مع `AB_TEST_FINANCE_SCHEMA=no` ثم نفذ الاختبار نفسه.

**لا تُشغّل fixtures على Supabase/Render، ولا تستخدم بيانات حقيقية.** مخطط 009 لا يحتاج مكتبات إضافية أو مزوداً خاصاً؛ PostgreSQL ومراجع التخزين المشفر قابلان للنقل. صلاحيات SQL تمنع حذف تاريخ المالية ولا توسع منح الأدوار القائمة.

## القرار المطلوب بعد المراجعة

مراجعة 009 ودليل الحسابات ونطاقات التفويض أولاً؛ ثم موافقة منفصلة على تطبيقه تجريبياً، وإسناد الصلاحيات التي يختارها المالك، وتشغيل فاحص الملفات، واختبار Supabase ببيانات وهمية. دمج الفرع ونشر Render إجراءان منفصلان ينتظران موافقة صريحة. لا يفعّل هذا PR أي نشر أو ترحيل سحابي.
