# Owner-managed test users

This feature is restricted to the existing `ab-group-demo.onrender.com` staging origin and pinned Supabase test project. No production enable flag exists. Managed test identities (including subsequently created users in their fictional tenant) cannot log in when the test environment binding is absent. The actual existing owner identity and password are never reset.

The approved catalog contains ten roles: owner, general_manager, regional_manager, hr_manager, pr_manager, marketing_manager, finance_manager, employee, investor and marketing_company. Provisioning checks actual role/permission rows before creating anything; it adds no roles, grants or migration. Collection manager/collector, government representative, development employee and deposit officer are not invented or mapped silently. In particular, a finance role does not automatically acquire newer delegated bank/ledger permissions absent from the approved catalog.

One owner per group remains enforced. All managed fictional users are created with real Supabase Auth identities in a NEW fictional organization with one fictional company. A sealed, non-password registry links these identities to the existing owner's organization and to the fictional owner's organization. Membership and role assignments are scoped to the new group. The single-company membership does not narrow legacy group-wide role permissions; no company-only restriction is claimed where the approved role itself grants group-wide access. No existing user is selected merely because their username starts with `test_`.

The dedicated owner-only API validates the sealed registry, live database identity, role, email, test marker and Supabase Auth identity/confirmation before any reset. It accepts no caller-supplied auth_id, role, tenant, email or password. Passwords are generated cryptographically on the server, verified against Auth and returned once over HTTPS. They expire for AB Group access after 24 hours. Password responses never enter request_dedup, settings, audit, localStorage, artifacts or logs. Prior application sessions are expired after reset. Browser display is masked, can be revealed/copied, and clears after a minute, closing, navigation, logout or hiding the page; the clipboard is controlled by the owner's device.

The owner opens **Test Users / تجربة المستخدمين** and uses **Set / reset** on a row, copies the one-time password, closes the dialog and signs in as that account. Reloading the table never retrieves a password. Repeated reset generates a different password and invalidates the previous one. The owner can suspend/re-enable the whole registered suite. Suspension is enforced at login and every API session and expires all suite sessions; it does not change the protected Owner role or database owner-status invariant. Other groups and real users are unaffected.

Provisioning uses protected `supabase-test` Actions secrets and an explicit active controller username `trial_4db27b82b8bf`. The job only accepts the fixed verification branch, project fingerprint, PostgreSQL Session pooler and restricted runtime role. A completed existing registry is preserved without replacement/reset. An explicitly enabled retry may resume an unfinished newly created suite within two hours: every sealed identity and confirmed Auth mapping is rechecked, the registered fictional Owner alone receives a bootstrap password, and other temporary passwords are set through the same owner-only API. This cannot target the real controller Owner. No test rows are deleted. New user passwords exist in memory only for real Auth/backend role checks and are discarded; owners obtain new ones through the screen. Tables of usernames/roles/results are safe to log, never passwords or tokens.

Regression checks include registry scope, owner-only API, real-account exclusion, CSRF, missing environment binding, reset verification, old-session invalidation, password nonpersistence, expiry, group suspension and real-owner/catalog preservation. The browser test covers Arabic/English desktop/mobile and the one-time dialog without screenshots or credential artifacts. The cloud fixture job uses the real Auth, runtime RLS and application server routes, including cross-tenant and financial denial checks, retaining all new fictional rows.

Authentication/deployment changes require the existing exact-commit staging approval gate; this feature does not weaken or self-approve that gate. No schema migration or new secret is needed. Existing encrypted backup/isolated restore and all staging CI gates remain required before Render publication.
