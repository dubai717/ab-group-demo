# Integrated TEST_DATA fixture

This is a create-only, versioned dataset for the existing managed-test-user group in the pinned Supabase staging project. It never creates/resets authentication accounts, adds roles/grants, moves existing users or edits existing company/customer/vehicle rows. The original controller Owner can view its summary; to open original record screens, use the existing registered test-group Owner (`test_owner_…`). The summary shows that workspace explicitly. This preserves tenant isolation rather than impersonating or expanding the original Owner's scope.

The dataset creates 5 companies, 7 bank accounts, 30 customers and 50 vehicles. Twelve vehicles have group funding with principal AED 10,000 / 15,000 / 20,000 / 25,000 and terms 12 / 16 / 18 / 20 months. It creates approved cash-custody examples, contract schedules, a reschedule within the original term and an extension request left awaiting approval. Service-only contracts, insurance/GPS installation records, number-fee/Salik/fine invoices and full/partial/unpaid collections exercise the existing domains. No real bank transfers occur; all financial journals are posted by the existing approved accounting functions and checked for balance.

Company and customer names, codes, traffic/Salik references, plates, VINs, contract legal-basis text, new chart items, tasks and document contents explicitly contain TEST_DATA. Banks use fictional names, alphabetic TEST_DATA account numbers, blank SWIFT and checksum-valid UAE IBANs with unassigned bank code 000. Contact phones use the NANP fictional 202-555-0100–0199 range, not real UAE subscribers; outbound consent is refused and messaging/tracking integrations remain disabled. No genuine identity numbers or legal documents are used.

The only trusted document decision is for byte hashes of PDFs generated within this fixture. All PDFs say TEST_DATA / FICTIONAL DOCUMENT ONLY and contain no executable content. This is NOT a replacement for a real malware scanner; normal uploads retain their existing quarantine behavior. Private document objects are encrypted using the current application format and uploaded to the existing private bucket without upsert. No storage settings or keys are changed.

Every newly inserted tenant row, including child history, invoices, receipts, journals, entries and notifications, is registered by its actual table/primary key in the sealed `TEST_DATA:integrated:v1` manifest. These tags establish provenance, not permission to delete shared counters or reference rows. There is NO deletion, bulk cleanup, reset or seeding endpoint in the web app. Any future cleanup requires separate approval and dependency checks.

The database phase uses the current domain handlers on an internal Fastify adapter which never listens on any port. It supplies the sealed, verified test Owner's existing authority and runs all writes as ab_runtime under tenant RLS. Public authentication and per-domain rights checks are unchanged. Existing user rows, memberships, grants and pre-existing business rows are compared before/after. New HR profiles and assignments only link task-capable existing test identities to new task data; existing login profiles, roles and company membership rows are not changed.

A dataset lock and the committed manifest make reruns idempotent. Domain records and their provenance manifest commit atomically. Generated encrypted object bytes are buffered in the sealed central manifest; no private object is uploaded before that commit. If storage fails, the manifest remains `files_pending`, and a retry uploads only missing identical objects at the already committed keys. A conflicting existing object stops the job; nothing is overwritten/deleted. Ready reruns verify and reuse the dataset without reposting balances or receipts.

The fixture deliberately uses Prospect for new/pending customers because Pending is not a supported customer status. It uses the current supported vehicle states Active/Pending/Terminated. Customer file dates are synthetic historical dates for these newly created rows; audit events still record actual creation time. Some customers have complete simulated documents and others are deliberately incomplete.

Area identifiers in the existing shared reference are strings such as `dubai:369`, not necessarily UUIDs. The customer address and vehicle registration/filter validators now accept those bounded identifiers while still verifying the selected area's emirate in the database. No region/reference record is replaced or duplicated.

The Owner-only Test Data panel reports actual persisted counts, not hardcoded totals, and links to existing company, customer, vehicle, bank, finance, task and report screens. It has no independent record editor and no active delete button. Role restrictions remain: finance/collection/vehicle powers are not invented for roles lacking existing delegations. Advanced reports, OCR, WhatsApp, external SMS/email, real GPS and production malware scanning are not activated by fixture data.

Cloud execution requires exact-candidate successful CI, the existing protected test environment, verified project/runtime-role bindings, a fresh encrypted backup with actual isolated restore, and the sealed current managed-test-user registry. The operations workflow is retained separately from the application delivery branch; it never invokes Render, applies SQL migrations, alters roles, creates a service or resets passwords. After successful seeding and validation, the application follows the existing controlled staging delivery and live checks. Production remains excluded.

## Deferred pre-production security review

On 2026-11-05 the owner authorized preserving the existing offline demo credentials while completing staging data. They are public, pre-existing fictional offline examples, not Supabase credentials. The deployed server serves `window.AB_CONFIG={central:true}`; the central adapter removes demo buttons, captures login submits and calls `/api/login`. That endpoint resolves only a registered central identity, verifies it through Supabase Auth and creates an HttpOnly server session; it never reads offline `app.js` passwords. A read-only cloud identity check must report no matching legacy demo usernames before this fixture writes data. No credentials are printed by that check.

Before operational/production use, review authentication end-to-end, remove/replace offline plaintext examples, verify fail-closed configuration and session handling, review recovery and rate limiting, audit role scopes and storage, and repeat penetration/security tests. This deferral does not certify production security and does not authorize a future production deployment.

## Catalog provenance correction

The initial live creation completed, but PostgreSQL catalog `name[]` values were returned as strings by pg, making the old key enumerator skip provenance tables. The enumerator now casts catalog identifiers to text[] and verifies that invoice/notification provenance is nonempty before committing a fresh fixture. No business data needs recreation. For the already-created version, the protected repair validates all five company roots share the same non-frozen PostgreSQL xmin, recovers row keys only from that creation transaction under tenant RLS, verifies every root/receipt/task relationship and the actual invoice/alert counts, excludes any account/grant/membership mutation, and updates only the sealed TEST_DATA manifest. Shared settings touched by creation are recorded separately and are never cleanup candidates. The repair is idempotent and does not repost balances, invoices, receipts, tasks or files.
