# Hosted backup / isolated restoration drill

## Scope and safety

The one-shot workflow `backup-restore-drill.yml` runs only from `verify/backup-restore-20261104`, using the existing `supabase-test` environment. It does not deploy or invoke migrations. Its source connection is the existing administrative Session pooler URL with verified TLS and `default_transaction_read_only=on`; every source transaction is read-only. Source database roles, permissions, passwords and objects are never changed.

The existing independent BACKUP key validation and AES-256-GCM archive format are reused. Key contents, data rows, provider messages and SQL errors are withheld. The restore target is hard-coded to a fresh PostgreSQL 17 container on the runner's loopback port 5547. Restore credentials cannot be selected from a source URL. The local database lives in tmpfs and has no application server or externally published port. The runner removes that container and its local ephemeral archive on completion, including failure. The explicitly approved retention mode keeps two encrypted objects in the existing private bucket; cleanup never touches those objects.

## What is checked

- The BACKUP key is canonical base64, exactly 32 bytes, and different from DATA_ENCRYPTION_KEY.
- All eight existing ledger entries match approved hashes; this drill refuses any additional migrations.
- A single exported repeatable-read snapshot binds source-table digests to the PostgreSQL custom-format dump.
- Scope: ab, public, auth and storage schemas, plus bytes of objects in ab-private-test. Provider platform settings, role passwords, API keys and data-encryption keys are intentionally not included.
- Private objects are reread for concurrent-change detection; encrypted archive authentication and each component digest are verified.
- Restore uses available local extension prerequisites and local NOLOGIN roles; unsupported dependencies must fail the restoration, not be stripped to produce a false pass. Role password/LOGIN restoration and provider control-plane recovery are outside this drill.
- Source/restored table sets, row counts and row-content digests, constraints, RLS flags/policies and non-internal triggers must match. Restored document references must resolve to restored object bytes; encrypted document payloads must decrypt with the existing data key and match their recorded SHA-256.
- The isolated runtime role must see no company rows without tenant/user context. This is a clone check, not a live hosted application test.
- The source ledger is rechecked at the end. No operation in the drill writes source data; concurrent external writers cannot be ruled out by a read-only observer.

## Retention and readiness limits

This workflow uploads no dump, archive, row manifest or keys to the public repository or Actions artifacts. In ephemeral mode it proves restoration only while its runner exists. With AB_BACKUP_RETAIN_APPROVED=private-bucket-no-overwrite, owner-approved retention writes the encrypted archive and encrypted metadata to unique paths in ab-private-test. It verifies public=false, existing size/MIME restrictions, create-only POST with x-upsert=false, downloaded byte hashes, anonymous public-access denial and actual restoration from the downloaded archive. Metadata is uploaded only after restoration succeeds. Any failure retains objects already created without deletion or replacement; inspect the fixed status and location before deciding what to do next. This is not a scheduled retention policy or complete provider disaster recovery.

Before migrations or deployment, arrange an explicitly approved restricted archive destination, independent key custody and retention, then capture a fresh backup and retain its digest-bound restore evidence. A new storage service, settings change or secret change requires owner approval. Do not activate deployment or change the existing staging branch merely to run this drill.

## Approved retained backup mode (2026-11-04)

Only new ciphertext objects under `ab-group-backups/v1/<UTC timestamp>-<UUID>/database.abbackup` and `metadata.abmeta` are created. The metadata is also AES-GCM sealed with the independent backup key and contains verification facts, not encryption keys. No bucket PATCH, object PUT/upsert or DELETE is used. Existing backup paths are excluded from object-byte capture to prevent recursive archive growth; their source storage metadata remains in the SQL snapshot and their existing archives remain untouched. Application documents are still captured and verified.

The hosted SQL source stays read-only. The only approved hosted writes are these new Storage objects and the metadata generated by Storage for them. No application data, schema, privileges, secrets or bucket settings are modified. All eight migration ledger hashes must still match at completion. The workflow does not restore anything over Supabase.

This is a persistent copy inside the SAME Supabase project, not an off-provider backup. Loss of the whole project could also lose this copy. Preserve the independent backup key and the application data key separately; no key is placed in an archive or sidecar. Verify backup freshness again before any later approved migration/deployment.
