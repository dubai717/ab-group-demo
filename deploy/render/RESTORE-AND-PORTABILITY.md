# Staging backup, recovery and portability — preparation only

No cloud backup schedule, restore, service, billing or deployment is enabled. Existing source, eight applied migrations, RLS and data remain unchanged.

## Prepared capture

`backend/deploy/backup-staging.ts` runs only on the approved GitHub staging branch with AB_BACKUP_APPROVED=yes. It uses a separate administrator connection, never the web runtime. A repeatable-read, read-only snapshot feeds pg_dump (custom format, verified TLS, password in child environment only); ab/public/auth/storage schemas and data are encrypted in memory with the existing archive helper. All objects found in the private bucket are downloaded read-only, bounded to 64 MiB combined dump/object input, and included as bytes. No plaintext dump or object file is written. Role flags (not role passwords), policies, migration checksums and restoration context are included. The resulting exclusive-write .abbackup is checked by decrypting it in memory. Archive integrity verification is **not** a demonstrated cloud restore.

BACKUP_ENCRYPTION_KEY must be an independent canonical Base64 32-byte key held in the approved backup runner secret store AND in the owner's separate password manager. DATA_ENCRYPTION_KEY is not replaced or bundled; keep its protected independent recovery copy. Supabase API keys, database-role passwords, Auth external-provider settings and signing configuration are not treated as recoverable merely from pg_dump. auth.users includes sensitive identity hashes inside the encrypted dump; never expose raw exports or dump logs.

The template `.github/workflows/staging-backup.yml.example` is not an active workflow and does not upload archives. No recurring resource/cost exists. Before enabling, choose an approved private off-site destination, confirm who holds keys and approve capture/storage permissions. Do not put ciphertext and its decryption key in the same artifact or log. Suggested retention: 7 daily copies and 4 weekly copies (35 days). GitHub public artifacts must not become the default repository for sensitive backups just because an upload action exists.

GitHub schedules use workflow files on the default branch; staging-only code does not magically create a nightly schedule. Nightly execution therefore requires a separately approved minimal default-branch workflow (no automatic merge authorized) OR an approved external scheduler. A Render cron service would be an extra paid resource and is excluded from the USD 7 single-service estimate. Until selected, backup execution is prepared/manual only, not an operational daily backup claim.

## First isolated recovery drill — needs separate target/resource approval

1. Verify a successful encrypted capture, archive hash, keys and compatible pg_dump/pg_restore major version (source PostgreSQL 17 currently; verify actual server version first). Create/use an explicitly approved EMPTY ISOLATED recovery target; never restore to ab-group-erp-test or a production database.
2. Decrypt only on a protected temporary worker. Read the archive's restoration context, verify all checksums, inventory tables/rows, document versions, object bytes, foreign keys, RLS/policies and role attributes. No --clean or reset against the source.
3. For compatible Supabase targets, follow Supabase's supported migration/restore procedure for managed Auth/storage schemas, ownership and grants. Do not blindly pg_restore managed schema DDL or apply source superuser ownership to a different provider. Restore app data and migrate Auth identities/hash compatibility and private objects through reviewed provider tooling. Existing fixture-based local restoration tests do not establish managed Supabase Auth restoration.
4. Provision only the same constrained application roles on the NEW target under explicit approval. Database password credentials are restored through its secret manager (SCRAM=4096 for the Session pooler), not copied from role catalogs. Preserve permission scope and table/function ownership intentionally. Invalidate sessions on the restored target only before access; do not invalidate source sessions.
5. Restore private object bytes/names and metadata associations; retain immutable versions/quarantine status. Verify attachments can be decrypted using the original DATA key. Compare counts/IDs/FKs/audit history, login, company/bank retrieval, account scope denial and anonymous object denial. Record actual RPO/RTO; initial planning targets are RPO 24 h and RTO one working day, not a guarantee.
6. Keep restored records. No automatic cleanup/deletion, DNS switch or promotion. Report results for approval before any migration/cutover.

## Portability

Dockerfile.staging builds one non-root Node 24 container; source frontend is served by the same application origin. It has no bundled credentials, persistent disk dependency, managed Render database, Redis or Render-specific application API. PG storage uses ordinary PostgreSQL tables/migrations and transaction-local tenant context. AuthProvider/ObjectStore interfaces already isolate Supabase HTTP calls. Moving the Node service is straightforward; migrating Supabase Auth/password hashes, storage configuration and managed roles/SECURITY DEFINER ownership needs adapters and a real isolated compatibility drill. It is not a one-click guarantee. Back up the migration ledger and current code SHA together. Future migrations remain explicit, forward-only and separately approved; startup/build never runs them.
